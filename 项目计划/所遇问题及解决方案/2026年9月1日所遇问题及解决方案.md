# 2026年9月1日所遇问题及解决方案

## 一、文档整理任务：超长文本反复「sections 不能为空」+ AttributeError（已修复）

### 问题现象

用户在聊天框粘贴约 13000 字、含 20+ 表格的报价文档，要求生成 Word/PDF，任务**反复失败**：

1. 连续 5 次以「工具执行异常：sections 不能为空：请提供文档章节内容」收场；
2. 最后一次变成「工具执行异常：AttributeError」。

此前同链路曾出现「PDF 图片列缺失」「文件名不语义化」，本轮是新一组失败模式——**长文本**场景整体不可用。

### 根因分析

1. **「sections 不能为空」（LLM 输出截断）**：`generate_docx`/`generate_pdf` 只接受结构化的 `sections`，执行者 LLM 必须把 13000 字原文手工转成 sections JSON——输出 token 超限导致 JSON 截断，`executor.py` 的 `json.loads` 失败后 `args={}`，sections 为空被工具拒绝。这是「让 LLM 手工转写超长结构化数据」的模型能力边界，不是参数问题。
2. **AttributeError（sections 含非 dict 元素）**：`generate_pdf.py` L360 与 `generate_docx.py` L346 的 `(sec or {}).get("heading")` **无 isinstance 保护**——LLM 传入非空但含非 dict 元素（字符串）的 sections 时，`(sec or {})` 对非空字符串返回字符串本身，对字符串调 `.get()` 抛 `AttributeError: 'str' object has no attribute 'get'`。
3. **表格丢失（user 消息表格不提取）**：`fetch_session_messages.py` 的 `_extract_markdown_tables` 只扫 `assistant` 消息（`if role != "assistant": continue`），用户粘贴在 `user` 消息里的 markdown 表格提取不到；且两个文档工具都没有「原文渲染」能力，表格必须靠 LLM 手工转 `table` JSON——同样受 token 超限影响。

### 解决方案

把「LLM 手工转写」改为「后端直接渲染原文」：

1. **`generate_pdf.py` / `generate_docx.py` 新增 `content` 参数（原文 markdown 渲染，最高优先级）**：
   - 新增模块级 `_parse_markdown_blocks(content)`，把原文解析为块列表：`#`/`##`/`###` 行 → 标题（pdf 用 heading/subheading 样式、docx 用 `add_heading` 1~3 级）；markdown 表格块（`|---` 分隔行，复用 `_parse_markdown_table`）→ 表格渲染（图片列 `![alt](URL)` 保留嵌入）；`- `/`* ` 行 → bullets；`1. ` 行与其余 → 段落（`_safe_text` 清洗）。
   - `content` 非空时**跳过「sections 不能为空」校验**；渲染顺序：封面 → content 原文 → sections（补充分析）→ markdown_tables → 独立 images。
2. **修畸形 sections 的 AttributeError（两个工具同改）**：`for raw in sections: sec = raw if isinstance(raw, dict) else {}`，非 dict 元素跳过不抛异常。
3. **`fetch_session_messages.py` 扩展提取 user 消息表格**：`_extract_markdown_tables` 去掉 `assistant` 限定，同时扫描 user 与 assistant 消息——用户粘贴在聊天框的原文表格也能进入 `markdown_tables` 自动注入。
4. **`executor.py` 系统提示更新**：文档整理类任务新增「超长原文直接传 content」指引——`>2000 字或含大量表格` 时把 `fetch_session_messages` 读到的用户消息原文按序拼接放进 `content`，禁止手工转 sections JSON；短文本仍用 sections。同时 markdown_tables 自动注入逻辑加 `not args.get("content")` 条件（executor 已传 content 时不重复注入，防表格重复渲染）。
5. **`registry.py` schema**：generate_pdf / generate_docx 的 parameters 补 `content` 字段描述，`required` 由 `["sections"]` 放宽为 `[]`（content 场景不强制 sections）。

### 改动文件清单

- `backend/app/core/agent/tools/generate_pdf.py`（新增 `_parse_markdown_blocks`、content 渲染、sections isinstance 保护、subheading 样式、校验逻辑放宽）
- `backend/app/core/agent/tools/generate_docx.py`（同上，docx 版）
- `backend/app/core/agent/tools/fetch_session_messages.py`（`_extract_markdown_tables` 扩展扫描 user 消息）
- `backend/app/core/agent/executor.py`（文档整理提示词补 content 用法；markdown_tables 注入加 content 排除）

### 反哺文档

- `项目计划/02_多Agents执行功能/04_生成PDF文件详解.md`：§5 数据契约补 `content`、§5.2 校验改「content/sections 至少其一」+ 非 dict 保护、§6 实现要点补 `_parse_markdown_blocks`；
- `项目计划/02_多Agents执行功能/05_生成Word文档文件详解.md`：§5/§5.1/§6 同上，§7 链路图补 content 分支；

- 提示用户：复制内容时尽量保留 markdown 表格格式；若已是纯文本表格，系统按段落渲染，表格结构需 LLM 修复（超长时仍可能失败，属模型能力边界）。

## 二、文档生成实测仍失败：Word AttributeError + 擅自改调 PDF（三根因二次修复）

### 问题现象

用户按「一」修复后实测：粘贴约 13000 字、含 20+ 表格的报价文档要求生成 **Word**，任务仍失败：

1. **Word 连续 2 次**「⚠️ 生成 Word 文档未成功（工具执行异常：AttributeError）」；
2. 执行者**擅自改调 PDF**：后续 4 次全是「⚠️ 生成 PDF 文档未成功（sections 不能为空：请提供文档章节内容）」；
3. 最终「❌ 执行达到最大工具调用轮次，任务未能完成」。

用户指出最痛的点：**要的是 Word，系统却中途换成 PDF 交付**——交付格式与要求不符比失败更可怕。

### 根因分析（三处，均已代码级坐实）

1. **Word AttributeError：图片收集循环对 None.table 调 .get**。`generate_docx.py` 与 `generate_pdf.py` 的图片收集循环：
   ```python
   for sec in sections:
       table = sec.get("table") if isinstance(sec, dict) else None
       for row in table.get("rows") or []:   # table 为 None → AttributeError
   ```
   2026-08-24 引入的图片收集循环缺 `if not table: continue` 守卫。LLM 按「一」的新提示词传了 `content`（原文）+ 若干**纯文字分析 sections**（无 `table` 键）→ 图片收集在第一个纯文字 section 上崩掉。此前测试场景 sections 全部带 table，被掩盖。
2. **「sections 不能为空」：LLM 输出截断后无兜底**。13000 字原文要求 LLM 手工回传进 content/sections，输出 token 超限 → args JSON 截断/为空 → `args={}` → 文档工具报「sections 不能为空」。executor 只兜底注入了 `markdown_tables`（表格原文），**没有兜底注入用户正文**——仍完全依赖 LLM 把 13k 字回传，必然截断。
3. **Word→PDF 中途换格式：纯 LLM 行为，提示词无硬锁**。generate_docx 失败后模型自行改调 generate_pdf（想"换个格式试试"），交付物变成 PDF。

### 解决方案（三管齐下）

1. **文档工具健壮性（generate_docx.py / generate_pdf.py 同改）**：
   - 入口防御：`params = params if isinstance(params, dict) else {}`（LLM 输出截断时 args 可能是 JSON 数组，`list.get` 会崩）；
   - 图片收集循环加守卫：非 dict section / 无 `table` 键的纯文字 section 直接 `continue`；
   - title 清洗字面 `\n` 换行为空格（LLM 传换行标题会崩封面排版）。
2. **executor 会话原文 content 兜底（根治截断）**：
   - `fetch_session_messages` 返回值新增 `assistant_tables`（仅助手消息提取的表格；用户表格已在原文里，避免 content 注入后重复渲染）；
   - executor 收集会话 user 消息 >300 字正文拼接为 `session_user_content`（`_strip_tail_instruction` 清洗末尾「请生成 word 文档」类指令句）；
   - 调 generate_pdf/generate_docx 时，`args.content` 为空或明显短于原文（`len < 原文×0.9`，疑似截断）→ 自动注入原文；
   - 表格分源注入：content 已注入 → 只注入 `assistant_tables`；否则注入全部 `markdown_tables`。
3. **提示词硬锁输出格式（executor.py 系统提示）**：用户要 word/文档/文件（未明确默认 Word）→ 只用 `generate_docx`；要 pdf → 只用 `generate_pdf`。**禁止因某格式工具失败改调另一种格式工具**（交付格式与要求不符是严重错误）；失败时改参数重试（content 传原文 / sections 精简），仍失败如实报告。

### 改动文件清单

- `backend/app/core/agent/tools/generate_docx.py`（params 归一、图片收集 None 守卫、title 换行清洗、残留 `(params or {})` 统一 `params.get`）
- `backend/app/core/agent/tools/generate_pdf.py`（同上）
- `backend/app/core/agent/tools/fetch_session_messages.py`（`_extract_markdown_tables` 加 `roles` 过滤参数；返回 `assistant_tables`）
- `backend/app/core/agent/executor.py`（`_strip_tail_instruction` helper；`session_user_content`/`session_assistant_tables` 收集；content 兜底注入 + 表格分源；系统提示补输出格式硬锁）

### 反哺文档

- `AGENTS.md`：多 Agent 任务约定「文档整理类工具」条目补 content 兜底注入 + 格式硬锁 + None 守卫一行摘要；
- `04_生成PDF文件详解.md` / `05_生成Word文档文件详解.md` §6：补非 dict params 防御、图片收集 None 守卫、title 换行清洗、executor 会话原文 content 兜底、assistant_tables 分源；
- `03_任务确认与执行详解.md` §5.7：补会话原文 content 兜底注入与输出格式硬锁两条。

### 验证结论

- `python -m compileall -q backend/app` 静态检查通过，无 lint 错误；
- 待用户手动 `python start.py --build` 实测：粘贴含表格原文 → 生成 Word，正文为原文全文（表格逐列渲染）、无 AttributeError、进度不再出现「生成 PDF」。

## 三、生成文档是一坨文字：0 表格 0 标题全文挤 1 段（根因链 + 换行保真修复）

### 问题现象

按「二」修复后实测「粘贴 13000 字报价文档生成 Word」：任务成功了，但生成的文档 **0 表格、0 标题，全文 7860 字挤在 1 个段落**里，用户评价「一坨屎」。另发现任务第 4 轮 reviewer 模型调用报 **`HTTP 402 Insufficient Balance`**（独立问题，见文末）。

### 根因分析（五段证据链，DB 与日志已坐实）

1. **前端单行 `<input>` 吞换行（根因）**：`ChatInput.jsx` 与 `DesktopAssistant.jsx` 的输入框是 `<input type="text">` 单行控件，浏览器对多行粘贴会**剥掉所有 `\n`**。DB 实测用户消息 7893 字符**零换行**（助手消息有 `\n`，证明存储链路不丢换行，丢在输入框）。
2. **executor 参数截断**：`agent_run_logs` 实测 generate_docx 两次 `args={}`——LLM 传 13k content 输出 token 超限截断，`json.loads` 失败回退 `{}`（触发「二」的兜底注入）。
3. **兜底注入压平原文**：「二」的 content 兜底注入的是 **DB 里的无换行文本** → `_parse_markdown_blocks` 对单行文本产出 1 个段落。
4. **渲染只认 markdown**：用户原文是**纯文本表格**（无 `|` 管道符，Tab/全角空格/单空格对齐 + 末列金额）与**中文编号标题**（`一、`/`（一）`/`1.1`，无 `#`）→ 表格/标题全部漏检。DB 原文实况：表头 `序号\t项目\t规格\t包干金额（HKD）`（Tab 分隔），数据行 `1 NAS 主机 x86_64 成品 NAS，4 盘位 7,000`（单空格对齐）。
5. **title 空**：文件名回退 `文档_20260901_095411.docx`（非语义化）。
6. **附带发现（非代码缺陷）**：任务第 4 轮 reviewer 模型调用 `HTTP 402 Insufficient Balance`——用户模型账号余额不足，需充值后任务才能完整跑通。

### 解决方案（治本：换行保真 + 纯文本结构识别）

1. **输入框 textarea 换行保真（治本，ChatInput.jsx / DesktopAssistant.jsx 同改）**：
   - 单行 `<input type="text">` → **`<textarea>`**：`rows={1}` + `onInput` 按 `scrollHeight` 自动增高（`overflow-hidden` + `resize-none`，最多 ~6 行后内部滚动）；`py-2` 微调适配多行；
   - **Enter 发送、Shift+Enter 换行**：`onKeyDown` 判 `e.key === 'Enter' && !e.shiftKey && !e.nativeEvent.isComposing && e.keyCode !== 229` 才发送（保留原 IME 保护与录音视觉态）；
   - placeholder 提示改为「Enter 发送，Shift+Enter 换行」。
2. **`_parse_markdown_blocks` 纯文本结构识别（generate_docx.py / generate_pdf.py 同改）**：
   - **中文一级标题**：`^[一二三四五六七八九十]+、` / `^第…[章节部分]` / `^（一）` → heading 1；
   - **编号二级标题**：`^\d+\.\d+` 且**行短（≤40 字）且不以数字结尾** → heading 2（防把 `1.1 基础环境搭建 … 7,000` 表格行误判）；
   - **文本表格块 `_split_text_table`（块级前瞻，保守）**：表头行可分列（**Tab 分隔优先**、全角空格次之、2+ 半角空格兜底，单空格不标准切）且（含「序号/项目/金额」等关键词 或 列数≥3）且首/末列非数字；数据行分列后（标准切，或**单空格对齐行「首列+中间+末列」3 列切分**）**首列序号数字或末列金额数字**，数据行 ≥2 才渲染为表格；表头列多于 3 时把金额末列**对齐到表头末列**（simple 切只有 3 列，避免金额错位到规格列）；表头前的行（如「（一）硬件费用　包干封顶价 HKD 13,000」）不吞进表格、由标题规则渲染；不自信回落段落。
3. **title 自动提取（文件名语义化兜底）**：`title` 空且 `content` 非空时取 content **首个非空行**（剥 `”`/`“` 引号与首尾空白，≤40 字）作 title——文件名不再回退「文档_时间戳」，如 `RR斜坡维修请求智能处理系统·NAS本地化部署方案与报价_20260901_102530.docx`。

### 改动文件清单

- `frontend/src/pages/DesktopAssistant.jsx`（文字输入兜底同样改 textarea：textAreaRef/autoGrowInput、Enter 发送/Shift+Enter 换行）
- `backend/app/core/agent/tools/generate_docx.py`（`_split_text_table`/`_split_cols`/`_is_num`/`_ZH_H1_RE`/`_NUM_H2_RE`/`_TABLE_HEADER_KW` 模块级；主循环补文本表格 + 中文标题判定；title 自动提取）
- `backend/app/core/agent/tools/generate_pdf.py`（同上，pdf 版）

### 反哺文档

- `04_生成PDF文件详解.md` / `05_生成Word文档文件详解.md`：§5 数据契约补 title 自动提取；§6 补文本表格/中文标题识别与 title 自动提取；
- `05_前端详解.md`：聊天输入框描述改为 textarea（Enter 发送 / Shift+Enter 换行 / 自动增高 / 换行保真说明）；
- `03_任务确认与执行详解.md` §5.7：补「换行保真依赖前端 textarea」一条；
- `AGENTS.md`：前端约定补「输入框 textarea 换行保真」一条。

### 验证结论

- `python -m compileall -q backend/app` 静态检查通过；`_parse_markdown_blocks` 用 DB 原文片段（Tab 表头 + 单空格数据行 + 中文标题）单元实测：`一、`/`（一）`→H1、`2.1`→H2、报价表识别为表格且金额对齐到「包干金额」列、正文/小结行回落段落、markdown 表格与列表路径不受影响；
- 前端改动不代跑构建，待用户手动 `python start.py --build` 实测：**在聊天框粘贴多行含表格文本（换行不再被吞）** → 生成 Word，段落/中文标题/报价表格（末列金额）逐块渲染、文件名语义化（取首个非空行），不再一坨文字。
- **⚠️ 独立提醒：模型账号当前余额不足（HTTP 402 Insufficient Balance）**——这是计费问题非代码缺陷，充值后任务才能完整跑通（审核者模型调用在第 4 轮中断）。

## 四、生成文档内容被 LLM 改写 + 20+ 表格只剩 1 个（原文直通 + 中文对照表识别，2026-09-01）

### 问题现象

用户粘贴 13000 字报价方案（含 20+ 表格、中文对照表、Tab 表头 + 单空格对齐数据行）要求「变成可下载的 word 文档」，得到的 docx 内容与原文**完全对不上**：章节名被 LLM 重写（如「三、本地化部署优点」变成别的措辞）、20+ 表格只剩 1~2 个、大量正文被总结压缩。用户质问「模型能不能把原文章直接变成 word，还是必须对内容进行更改」。

### 根因分析

1. **executor 链路让 LLM「提炼转写」而非「原文透传」**：即使系统提示已要求「超长原文直接传 content」，模型在逐 token 回传 13000 字全文时**输出 token 超限必截断**，退而求其次「按理解重写」——章节名、表格数量全变样（10:46 旧任务产物即此路径）；
2. **`_split_text_table` 只识别「首列序号/末列金额」的报价表**：用户原文大量**中文对照表**（如「评估维度 分析结论」表，末列是中文说明非金额）全部漏检 → 表格被当普通段落 → 一坨文字；
3. 旧任务产物还叠加了「旧单行 input 零换行」（台账三已修 textarea），但**即使换行保真后，LLM 改写 + 对照表漏检**两个问题依旧存在。

### 解决方案（原文直通 + 对照表识别，四轮修复）

**1. executor 默认原文直通（`backend/app/core/agent/executor.py`）**：
- 新增模块级 `_DOC_PASSTHROUGH_WORDS`（总结/提炼/精简/概括/缩写/改写/重写/优化/润色/摘要/要点/大纲/整理成表格/归纳）与 `_want_passthrough(task)`：task_type 为 generate 且描述/params 不含加工词 → True（用户要「原样变文档」）；
- 文档工具注入处改两分支：**直通（默认）**——若 `_want_passthrough(task)`，先用 `call_tool("fetch_session_messages", {"limit": 60})` 确保 `session_user_content` 已填充（模型没先调就主动拉），然后**无条件** `args["content"] = session_user_content`、`pop("sections")`、`pop("markdown_tables")`——正文完全用会话原文，LLM 只定格式（word/pdf）与 filename/title；**加工模式**（含加工词）——保留原有 content 兜底注入 + 表格分源注入逻辑；

## 五、生成文档仍是"一坨文字"：dist 未构建 + 零换行旧消息 + 规则猜格式失效（LLM markdown 化直通，2026-09-01）

### 问题现象

用户再次实测（19:35 生成 docx）后情绪崩溃：生成的 Word 还是**一坨文字**——全文挤在 1~2 个巨型段落里，没有标题样式、没有表格、没有分段，还混入了「变成可下载的word文档」指令句。用户强调「原样补充≠原样样式：文字内容一个标点都不准变，但格式必须美化——识别出表格就要渲染成表格、识别出标题就要有标题样式」。

### 根因分析（证据链，均已坐实）

1. **`frontend/dist` 从未重新构建（最隐蔽的根因）**：`frontend/dist/` 下主 JS 时间戳是 **2026-08-24 00:37**，且 `index-*.js` 中**不含 `<textarea`**——textaera 换行保真修复（09-01 做的）只改了源码、**从未 `npm run build`**。运行中的页面（nginx 托管 dist）仍是旧单行 `<input>`，粘贴照样剥掉所有 `\n`；
2. **DB 里所有 SRR 粘贴消息零换行**：`SELECT ... length(content), (content LIKE '%'||chr(10)||'%')` 查证——09-01 的 09:14/09:35/09:52/10:46/11:30 五条消息 `has_newline=f`（而 08-15 附件 PDF 消息 `has_newline=t`，证明后端不剥换行）；11:30 的消息在 textarea 修复之后仍零换行 → 用户修复后**没有重新粘贴**，19:35 docx 就是拿 10:46/11:30 零换行旧消息生成的；
3. **规则猜格式在零换行下一并失效**：`_parse_markdown_blocks` 的纯文本表格识别（Tab/空格对齐）与 `_strip_tail_instruction`（按行切找尾部指令句）都依赖换行结构；零换行时全文算 1 行 → 表格识别 0 命中、指令句因无行边界混进正文。

### 解决方案（LLM markdown 化直通：不再用规则猜用户输入）

1. **executor 新增 `_markdownify_content`（`backend/app/core/agent/executor.py`）**：
   - `_chunk_text(text, max_chars=2000)`：优先按 `一、`/`（一）`/`1.1` 等编号标题切块，否则在句号/分号/换行后切满 2000 字；每块以完整句子结束，实测零换行 631 字原文切 2 块、拼接字数守恒（632 vs 631）；

   - **任一块失败整体返回 None** → 调用方回落原文直接注入（不阻断任务）。
2. **文档工具注入改"先 markdownify 再注入"**：直通分支在注入 `args["content"]` 前先 `_markdownify_content(session_user_content, executor_cfg, summarize=False)`，成功则正文完全用 markdown（移除 sections/markdown_tables）；失败回落原文直接注入。加工分支 `summarize=True`，失败回落原 content 兜底注入逻辑。
3. **`_SYSTEM_PROMPT` 文档整理段更新**：明确"正文会由系统自动转成规范 markdown 并注入，无需也不得自行回传全文"。
4. **generate_docx / generate_pdf 不做大改**：标准 markdown 渲染路径已完整支持（`#`/`|` 表格/`-` 列表/段落）；`_parse_markdown_blocks` 的纯文本表格识别**保留为兜底**（兼容 markdownify 漏转片段）。

## 六、方案 C：直通去 LLM 化改造——规则打底 + LLM 只出标记指令，正文永不经过 LLM（2026-09-01 晚）

### 问题现象

用户拿同一份 13000 字报价方案分别给豆包与 XIAONA 生成 Word：豆包输出**与原文 100% 一致**（文字、表格、标题逐字还原），XIAONA 生成的内容仍被 LLM 改写/压缩/丢表格。用户追问「为什么我们做不到 100% 准确输出」——台账四/五的 LLM markdown 化（方案 B）本质仍是**让 LLM 逐字回传全文**，输出 token 超限必截断、退而求其次改写，无法保证逐字保真。用户拍板改**方案 C**：规则打底，LLM 只对规则吃不准的表格返回行级标记指令，程序在原行插入标记，**正文永远不经过 LLM**。

### 根因分析

1. **生成式 LLM 不适合做「逐字复制」**：13k 字原文要求 LLM 原样输出，token 上限内必然截断；截断后模型「按理解补全」= 改写/编造/丢内容（台账四/五已坐实）。豆包直通大概率走的是**纯规则透传**（不经模型或模型只标结构），所以能 100% 一致；
2. **规则渲染器在畸形输入下误判**：`_parse_markdown_table` 不剥 `| | a | b | |` 首尾空 cell（LLM 残留管道符 → 表头/数据列数对不齐）；`_split_text_table` 会把 markdown 表格行（含 `|`）与 `- ` 列表行误判成文本表格；`_parse_markdown_blocks` 只认 `---` 分隔行触发的表格（原文/LLM 输出常无分隔行）；
3. **零换行旧消息**：历史粘贴经旧单行 input 剥掉所有 `\n`，7800 字单行文本规则解析无从下手（台账三根因，虽已修 textarea，但旧消息无法恢复结构）。

### 解决方案（方案 C 三层）

**1. 规则渲染器修复（generate_docx.py / generate_pdf.py 同改）**：
- `_parse_markdown_table` **去首尾空 cell**：`| | 评估维度 | 分析结论 | |` split 后剥离首尾空串，列数才与表头一致；行须以 `|` 开头（防普通文本误入）；
- `_split_text_table` **拒绝含 `|` 的行**（markdown 表格交给 markdown 路径）与 **`- `/`* ` 开头行**（列表行）——此前 markdown 表格行会被单空格切分误判成文本表格、`- ` 列表行被当表格数据行；
- `_parse_markdown_blocks` 表格识别扩展为**连续 `|` 行**：首行 `|` 开头且次行也 `|` 开头即成表格块（不再强制 `---` 分隔行）；新增 `_strip_md_symbols` 剥离 `**`/`*`/`` ` ``/`~~` 符号（直通渲染不应出现 markdown 残留标记）。

**2. `_smart_break_lines` 零换行语义分行（纯规则、保真、不调 LLM）**：
- 只对**超长行（>100 字）**处理：在「中文编号标题（一、/第X章/（一））/数字编号标题（1.1）/编号列表项（1. ）/表格表头关键词行（序号/项目/金额…后跟 Tab 或全角空格）」前插 `\n`；
- **逐行处理**：已有换行文本不被破坏（短行原样保留，含 Tab 表格行）；压缩行内多空格但保留单 Tab/单空格（表格分隔不丢）；已有合理换行（≥6 个）整体不动；
- 断点正则 `_BREAK_RE` 的 sub 只插 `\n`（**勿用 `r"\n\1"`**——`\1` 会重复插入捕获的断点文本，实测产生 `2.1 2.1 总体结论` 式重复）。

**3. executor 直通改方案 C（正文永不经过 LLM）**：
- 新增 `_markup_document(text, cfg)`：先 `_smart_break_lines` + `_parse_markdown_blocks` 规则解析；统计「表格候选行」（含表头关键词/Tab/全角空格）与规则已识别表格行覆盖——覆盖 ≥80% 直接用规则结果（正文保真）；候选行 ≥4 且覆盖不足才**调一次 LLM**；
- 新增 `_ask_table_marks(lines, cand, cfg)`：候选行带行号发给 LLM，要求只返回 `{"marks":[{"line", "anchor"}]}`（锚定 = 该行开头 6 字，防行号漂移）；程序 `_split_cols` 切列后转 `| c1 | c2 |` 表格标记插入原行——**LLM 输出正文一律丢弃**，只取行号；
- 应用标记后**重解析校验**：新表格行覆盖 ≥80% 才采用，否则回落原文直注（宁可保真不保结构）；LLM 失败/超时/非法 JSON/候选行过多（>80）同样回落原文直注；
- 直通分支注入 `content` 时**同时 pop title/subtitle/date/source**：封面元信息由 LLM 编造会污染文档（如 date=2026-08-24 错误日期），title 由工具从 content 首行自动提取；
- **加工模式（总结/提炼/润色）保留 LLM 提炼**，且 `_markdownify_content` 改为**并行分块**（`asyncio.gather` + `Semaphore(4)` + 单块 `wait_for(180)`）——超长文档不再串行 4-7 次调用卡数分钟。

**4. 样式工程化（docx）**：`render_table` 加 `t.autofit = True`（Word 自动分配列宽）+ 表头单元格居中；PDF 侧列宽分配与表头/斑马纹样式已完备，未动。
