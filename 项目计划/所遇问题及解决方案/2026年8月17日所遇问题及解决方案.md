## 一、多 Agent 任务执行：确认/执行/会话留痕/渠道路由（02 子项目群首个实现）

### 背景需求

用户需求（2026-08-17）：在现有聊天链路上接入 02 文档的多 Agent 任务执行——交互者判断意图 + 反问确认，确认后才执行；执行者 function calling 调工具干活，审核者验收打回。三种渠道的任务处置：

1. **聊天页**：当前会话内确认 + 执行 + 留痕；
2. **桌面助手**：确认后**后端新建专属会话**（source=desktop），任务全程写入，用户回聊天页侧边栏可见；
3. **飞书注册用户**：任务写入飞书映射会话 + 回发飞书；
4. **飞书影子账号**：只执行 + 回发 + 追加「任务结果不保存」提醒，**不留痕**。

### 解决方案（实现全貌）

新增 `backend/app/core/agent/` 包（service/director/executor/reviewer/workflow/tools）与 `backend/app/api/agent.py`，改动 `llm_provider.py`（tools 支持）、`sql_models.py`/`database.py`（AgentTask/AgentRunLog 表 + FunctionAssignment 新列）、`chat.py`/`feishu.py`（接入 + SSE task_started 帧）、`settings.py`、前端 `Chat.jsx`/`Settings.jsx`/`api/chat.js`/`api/agent.js`。详细见 `项目计划/02_多Agents执行功能/03_任务确认与执行详解.md`。

### 关键设计决策

1. **确认交互复用聊天链路**：不单独做 `/api/agent/confirm` 接口，而是 `service.handle` 先查 pending 确认、再查新任务意图、都落空才回落 memory_engine——聊天/桌面/飞书三个端口只需把 `chat_core.chat` 换成 `agent_service.handle` 即可全量接入。
2. **SSE 加 `task_started` 帧**：确认后多一帧 `{"task_started": {task_id, session_id}}`，前端收到后开始轮询 `GET /api/agent/tasks/{id}`（每 3s），done/failed 停轮询并刷新消息。
3. **模型分配回退链**：`executor_cfg = executor || chat`，`reviewer_cfg = reviewer || executor || chat`（未分配审核者时回退执行者，避免「自己审自己」的单一模型风险降到最低，但用户可分别分配）。
4. **llm_provider 支持 function calling**：`_complete` 加 `tools` 参数，非流式响应含 `message.tool_calls` 时返回完整 message（由 `chat_with_tools` 消费）；普通聊天不受影响（tools=None 返回 content 字符串）。

### 验证结论

容器内跑通端到端断言（无 LLM key 时降级路径）：
- 意图预筛（扒/生成 Excel 命中、闲聊不命中）；pending 创建 + 确认文案；
- 确认流程：task_started 帧 + 目标会话确定 + 后台任务启动；状态 `confirmed → executing → failed`（无 key 执行者失败属预期降级）；
- 取消流程：`cancelled`；
- 工具层：generate_excel 落盘/行列校验/白名单拦截、fetch_url 抓 example.com 成功；
- API 路由 `/api/agent/*` 全部注册成功；DB 迁移（function_assignments 新列 + agent_tasks/agent_run_logs 建表）验证通过。

> 有 API Key 的完整链路（真实执行 + 审核通过 + 产物下载）需配置 `OPENAI_API_KEY` 后浏览器实测。

## 四、飞书长连接接入（替代 Webhook + ngrok）

> **⚠️ 已回退（2026-08-17 晚）**：长连接接入已整体删除，回归**公网 Webhook**。用户实际用的是公网连接（ngrok + 请求地址），长连接「连不上」，且文档被误写成长连接导致混乱。回退细节见下方「八、飞书长连接回退为公网 Webhook」。以下为当时长连接实现的原始记录，保留供追溯。

### 背景需求

用户需求（2026-08-17）：飞书集成从「Webhook + 公网地址（ngrok）」切换到**官方 SDK 长连接**模式——程序主动连飞书，彻底摆脱 ngrok/公网/HTTPS 依赖。

### 解决方案（实现全貌）

1. **依赖**：`backend/requirements.txt` 新增 `lark-oapi==1.7.2`（pip 可装最新版，用户确认的依赖例外）。
2. **核心重构**：`backend/app/api/feishu.py` 把 webhook 第 3 步起的消息处理逻辑整体抽出为 `process_feishu_event(event, event_id)` 统一入口——去重 → 会话映射 → 媒体/音频/文本分流 → 影子账号 → agent/chat → 回复发送 → 后置标记已完成。webhook 接口保留（签名验证 + challenge + 调 `process_feishu_event`），长连接也调它，逻辑不双份漂移。
3. **新增长连接客户端** `backend/app/core/feishu_ws.py`：`lark-oapi` 的 `ws.Client.start()` 是阻塞同步方法，且 SDK 模块级缓存 asyncio loop（issue larksuite/oapi-sdk-python#119），故用**独立守护线程**跑 `ws.Client`，线程内 `asyncio.new_event_loop()` + patch `ws_client_mod.loop`；事件回调同步函数用 `asyncio.run_coroutine_threadsafe(process_feishu_event(...), main_loop)` 调度回 FastAPI 主事件循环。
4. **启动接入**：`main.py` lifespan 里 `FEISHU_APP_ID` 与 `FEISHU_APP_SECRET` 均非空时 `start_feishu_ws(asyncio.get_running_loop())`。
5. **环境变量**：`.env` 填入真实 `FEISHU_APP_ID` / `FEISHU_APP_SECRET`；`FEISHU_VERIFY_TOKEN` 长连接模式不需要；`FEISHU_BOT_OPEN_ID` 群聊 @ 判断用（单聊测试可暂缺）。

### 关键坑（踩过两次）

- **`asyncio.get_running_loop()` 不能放 `asyncio.to_thread` 里**：第一版把启动包成 `asyncio.create_task(asyncio.to_thread(_start_feishu_ws))`，线程池线程没有运行中的事件循环，`get_running_loop()` 抛 `RuntimeError`，异常被 create_task 吞掉 → 长连接**静默不启动**，日志里完全没有 feishu 相关输出。修复：`start_feishu_ws` 本身只创建后台线程不阻塞，直接在 lifespan 主协程里调用 `asyncio.get_running_loop()` 取主 loop 传入。
- **SDK 模块级 loop 需 patch**：`ws.Client.start()` 源码用模块级 `loop.run_until_complete(self._connect())`，不 patch 会拿主线程已运行的 loop → `RuntimeError: This event loop is already running`。必须在后台线程内 `asyncio.set_event_loop(loop)` + `ws_client_mod.loop = loop`。

### 验证结论

- `python -m compileall` 通过；容器内 `lark-oapi` 1.7.2 import 成功、`EventDispatcherHandler.builder("","")` 注册回调成功、`lark.JSON.marshal` 可用、`ws.Client.__init__` 签名确认、`Client.start()` 源码确认走模块级 loop；
- 后端镜像重建 + `up -d` 重启，健康检查通过；
- 事件结构确认：长连接 `P2ImMessageReceiveV1` = `EventContext{header{event_id,...}, event{sender, message}}`，与 webhook 的 `payload["event"]` 结构一致，`process_feishu_event` 共用无适配成本。

## 五、Compose 读不到根目录 `.env`（`--env-file` 缺失）

### 问题现象

`.env` 填了 `FEISHU_APP_ID`/`FEISHU_APP_SECRET` 且镜像已重建，但容器内 `env | grep -i feishu` 全部为空、长连接日志不出现。

### 根因分析

Docker Compose 的 `.env`（变量替换源）默认从 **compose 文件所在目录**（`backend/`）查找，而本项目 `.env` 在**项目根目录**。此前 `DB_PASSWORD`/`NEO4J_PASSWORD` 等恰好与 `docker-compose.yml` 内置默认值相同（都是 `xiaona_pass`），所以读不到也没暴露；非默认值（飞书凭据）就失效了。

### 解决方案

- `start.py` 启动命令加 `--env-file`：`docker compose --env-file <根目录>/.env -f backend/docker-compose.yml up --build`；
- 手工执行 compose 同样带 `--env-file .env`；
- `.env.example` 飞书段注释同步说明长连接无需 VERIFY_TOKEN。

### 验证结论

`docker compose --env-file .env -f backend/docker-compose.yml config` 解析出 `FEISHU_APP_ID: cli_aa08da763c781bc4`；重建容器后 `env | grep -i feishu` 命中，日志出现 `[Lark] connected to wss://msg-frontier.feishu.cn/...`。

## 六、机器人 open_id 不在后台 UI，需调 bot/v3/info 获取

### 问题现象

用户在「凭证与基础信息」页面只看到 App ID / App Secret，找不到 `FEISHU_BOT_OPEN_ID`（群聊 @ 判断配置项）。

### 根因分析

飞书后台**不展示**机器人的 open_id。官方唯一获取方式是调接口 `GET /open-apis/bot/v3/info`（携带 tenant_access_token），响应 `bot.open_id`。该接口无需额外权限，有 App ID/Secret 能换到 token 即可。

### 解决方案

容器内临时脚本复用 `FeishuClient.get_tenant_token()` 拿到 token，再 GET `bot/v3/info`：

```python
# 关键行（临时脚本，用后即删）
token = await fc.get_tenant_token()
resp = await client.get("https://open.feishu.cn/open-apis/bot/v3/info",
                        headers={"Authorization": f"Bearer {token}"})
# 响应 code=0 → data["bot"]["open_id"]
```

### 验证结论

取到 `ou_49f2ec743c93f7b1e1f951b1260714c9`（应用 activate_status=2 已启用），写入 `.env` 后重启，容器内 `env | grep FEISHU_BOT_OPEN_ID` 命中，长连接重新 `connected to wss://...`。群聊 @ 判断从名字兜底升级为 open_id 精确匹配。

## 七、飞书影子账号机制废弃 + 账号绑定改造（2026-08-17 设计定稿，待实施）

### 背景与问题

飞书接入后用户发现：**未绑定的小娜账号用户在飞书里发消息，会被自动创建「影子账号」并尝试聊天**。经排查与用户讨论，这套「影子账号」机制必须整体废弃：

1. **陌生人白耗 token**：任何人在飞书发消息都会自动建影子账号并调 LLM（走的还是主人配置的大模型），1 万陌生人可薅空额度；
2. **影子账号无模型配置**：新账号没有任何 `function_assignments`，`chat_core` 必然抛 `ChatModelNotConfigured` → 500，用户看到的是「怎么发都没反应」；
3. **无绑定入口**：系统没有「open_id ↔ 正式账号」关联能力，飞书通道无法进入正式账号；
4. **用户澄清关键认知**：飞书侧**无法拿到手机号**，只能拿 `open_id`；「一个小娜（一个手机号账号）可接多个飞书 open_id」，多个飞书账号共享同一账号的三层记忆。

### 确定的新机制（设计定稿）

- **核心原则**：小娜是「贴身秘书」，只服务已绑定账号的主人。**未绑定 open_id 发消息 → 不创建账号、不调 LLM，只回 0 token 固定引导文案**，任何陌生人无法消耗主人 token；
- **绑定 = 手机号 + 密码 + 短信验证码 三步验证**，全程在飞书对话框分步引导（一步一问，避免整串输入格式错误）：
  1. 用户报手机号 → 查账号表（不存在 → 「该手机号未注册，请先到官方网页注册」）；
  2. 用户报密码 → `verify_password`（错误 → 「密码错误，请到前端界面修改密码」，不退回手机号）；
  3. 密码正确 → 发短信验证码 → 用户报验证码 → `verify_sms_code` → 写 `feishu_user_map(open_id → user_id)` → 绑定成功；
- **安全硬性要求**：绑定指令（含密码）在进入聊天流程前拦截，**不落库、不进记忆检索、不进日志**；绑定中间状态（等密码/等验证码）存模块级内存 dict（按 open_id 索引，5 分钟 TTL）；
- **一个小娜账号可绑多个飞书 open_id**（`feishu_user_map.feishu_user_id` 去 unique 约束），同手机号注册的多个飞书账号共享同一账号三层记忆；
- **设置页**：已绑定显示绑定身份列表（open_id 后 8 位 + 绑定时间 + 最后活跃），每项可解绑（手机号+验证码确认，三层记忆保留）与修改密码（手机号+验证码+新密码）。

## 八、飞书长连接回退为公网 Webhook（2026-08-17 晚）

### 问题现象

用户明确反馈：**飞书接入用的根本不是长连接，用的是公网连接**（事件订阅里填了 ngrok 公网地址的 Webhook），但代码与文档被写成了「长连接」，且长连接「连不上」。要求把长连接**直接删掉**。

### 根因分析

- 飞书开放平台事件订阅有两种接收方式：Webhook（填公网请求地址，飞书 POST 推送）与长连接（官方 SDK 主动连飞书）。用户实际配置的是 **Webhook + 公网地址（ngrok）**；
- 之前曾按「切换到长连接」的计划实现了 `feishu_ws.py` + `lark-oapi` 并写入文档（10 §8.1、AGENTS.md），与用户实际使用方式矛盾，且长连接连接不上，造成混乱；
- 文档与代码对长连接的大量描述（默认接入方式、环境变量注释、验证步骤）需要整体清除。

### 解决方案（回退为纯 Webhook）

1. **删除** `backend/app/core/feishu_ws.py`（长连接客户端整个文件）；
2. **`backend/app/main.py`**：lifespan 删除长连接启动块（`if FEISHU_APP_ID and FEISHU_APP_SECRET:` → `start_feishu_ws`），并删除 import 中的 `FEISHU_APP_ID` / `FEISHU_APP_SECRET`；
3. **`backend/requirements.txt`**：删除 `lark-oapi==1.7.2` 及注释；
4. **`backend/app/api/feishu.py`**：`process_feishu_event` 保留（webhook 主路径在用），docstring/注释去掉「webhook 与长连接两个入口共用」「10 §8.1」等表述；
5. **`项目计划/01_单Agent聊天助手/10_飞书IM机器人接入详解.md`**：§3 恢复 Webhook 事件订阅配置（填请求地址 + 加密策略）；§8 恢复为「本地调试（Webhook 模式）」主路径；**§8.1 长连接整节删除**；§9 技术栈删 `lark-oapi`、补 `pycryptodome`（事件解密）；
6. **`AGENTS.md`**：「飞书长连接约定」整节改写为「飞书 Webhook 约定」（公网 webhook + 签名/解密 + `process_feishu_event` 唯一入口）；
7. **`.env.example`**：飞书段恢复 webhook 说明——`FEISHU_VERIFY_TOKEN` 必填（签名）、`FEISHU_ENCRYPT_KEY` 事件加密时必填，删除「长连接模式无需 VERIFY_TOKEN」注释；
