## 二、Agent 三处高优先级代码 Bug 修复（2026-08-19）

### 背景需求

在上节全量审核的**代码侧**复核中，发现多 Agent 任务系统有 3 个 P0/P1 真实 bug。用户确认只修这 3 处代码 bug（其余低优先级项列入后续）。

### Bug 清单与根因

1. **「没问题」被误判为取消任务**（`director.py` `classify_confirmation`）：
   - 原快速判定**先判取消词再判确认词**，`_CANCEL_WORDS` 含「没」，「没问题」是最常用肯定答复却命中「没」→ 返回 `no`，任务被误取消。
   - 修复：判定顺序改为「强肯定短语 → 强否定短语 → 弱否定 → 弱肯定 → LLM 兜底」。`_STRONG_CONFIRM` 含「没问题/可以/好的/好/行/确认/执行/开始/ok/yes」等，先于否定判定拦截；`_STRONG_CANCEL` 含「不是/不用/不要/取消/算了/放弃/不了/等等/再说/no」；`_WEAK_CANCEL` 含「不/没/否」；`_WEAK_CONFIRM` 含「是」。注意「不是」含「是」，强否定必须先于弱肯定。

2. **pending 任务跨会话/跨渠道串扰**（`service.py` `_latest_pending`）：
   - 原实现只按 `user_id` 取最近一条 pending，不区分会话/渠道。web 某会话有待确认任务时，用户在**另一个会话或飞书/桌面**发任意消息都会被 `classify_confirmation` 判定为确认/取消/其它——可能误确认或误取消任务（feishu.py 三处 `agent_service.handle` 调用同样受影响）。
   - 修复：`_latest_pending(user_id, session_id, channel)` 增加 `session_id` + `channel` 过滤；调用处传 `sid` 与 `_channel(source)`（pending 创建时就是当前会话+渠道，天然匹配）。

3. **任务后台执行同步落库阻塞事件循环**（`workflow.py` `_write_message`）：
   - 原为同步函数直接调 `memory_sql.save_chat_message(write_chroma=True)`，embedding 为 CPU 密集操作（0.3~数秒），任务执行期间**全站 chat_stream 卡顿**——违反 AGENTS.md「同步落库 + embedding 一律走 asyncio.to_thread」，与台账十六（8月16日）修过的同类问题一致。
   - 修复：`_write_message` 改 `async def`，内部 `asyncio.to_thread` 包裹 `save_chat_message`；`start_task_async` 内 5 处调用点（L150/160/175/196/233）全部加 `await`。`_status`/`_log`/`_load_task`/`_persist_artifacts` 为轻量查询保持同步。

### 验证结论

- `python -m compileall -q backend/app` 通过；
- 判定逻辑单测：`没问题/好的/好/可以/ok/确认/开始吧/同意` → yes；`不是/不用了/取消/算了/不要/不/没/否` → no；`嗯/你说呢/空` → other，19 个用例全过；
- grep 确认 `_latest_pending(` 定义与调用均已带 session_id + channel 参数；
- 行为推演：web 会话 A 有 pending 时切到会话 B 发消息 → 不再命中 pending，走正常聊天链路。

## 三、电商数据源落地（02 爬取 Phase 1，2026-08-19）

### 背景需求

用户要求「搜索北美卖得最好的戒指 top10」这类问题能返回**可看可点的榜单**（图片 + 链接 + 细分品类筛选 + 排名范围），并明确：
1. **只要北美数据**（不要香港数据）；
2. Amazon 无 API key 作为**保底数据源**；
3. 用户提供其它 API key 时与 Amazon **交叉验证**；
4. 设置页新增**数据源 API key 管理模块**（可填可不填）。

### 遇到的问题与根因

1. **香港 IP 返回 HKD 价格**（`_diag_amazon_tmp.py` 实测）：服务器出口 IP 被 Amazon 判定为香港，BSR/搜索页默认返回港币。**根因**：Amazon 按 IP 地区本地化价格。**修复**：请求带 `i18n-prefs=USD` + `lc-main=en_US` cookie + `Accept-Language: en-US` 强制美元/英文渲染（实测 fashion 页 footer 出现 "$ USD - U.S. Dollar"，价格由 HK$ 变 $）。
2. **BSR 类目页 nodeId 重定向回大类**：`Best-Sellers-Jewelry-Rings/zgbs/fashion/7141123011`（实测）返回「Best Clothing, Shoes & Jewelry」大类（Hanes 内衣占榜）而非戒指榜——Amazon 服务端忽略 nodeId 回退大类。**修复**：主路径改为**搜索页按人气排序**（`/s?k={关键词}&s=exact-aware-popularity-rank`，天然按销量热度排序且关键词直接命中细分品类）；显式 `url` 传 BSR 页时仍走榜单页解析。
3. **Amazon 搜索页 HTML 结构变化**：`data-cy="title-render"` / `s-link` 锚点已失效，且 `_depth` 状态机因 starttag 对全标签 +1、endtag 只对 div -1 导致卡片不关闭、串卡；还误抓「Results/More results」导航卡。**修复**：重写 `_SearchParser`——去 depth 依赖，以「卡内出现 `/dp/` 商品链接」为收卡/过滤条件；图片 `s-image` src、标题 `h2`、价格 `a-offscreen`、评分 `a-icon-alt`、评论数 `s-underline-text` 直接写入当前卡。实测 8 条 silver ring 全带图片/价格/评分/链接。
4. **中文关键词 0 结果**：`category=银戒指` 直接搜索返回空——Amazon 只索引英文标题。**修复**：内置 `_ZH_TO_EN` 中英品类映射（银戒指→silver ring、钛钢→titanium steel 等，长词优先替换）。
5. **Amazon 频控触发 `bm-verify` 浏览器验证**：短时间内多次请求后返回 2KB 挑战页（meta refresh + bm-verify token）。**修复**：工具内置 `_is_bot_check` 检测（bm-verify / Robot Check / "enter the characters"），触发时返回中文提示「Amazon 触发了浏览器验证（频控/反爬），请稍后重试或降低请求频率」，不再返回误导性空结果。
6. **Etsy key 从 .env 改 per-user**：用户要求设置页可配置各数据源 key。**修复**：新增 `DataSourceConfig` 表（user_id + source 唯一），`GET/PUT /api/settings/datasources`，`_resolve_api_key` 回退链 `ctx.user_id` 查 DB → env `ETSY_API_KEY`。Amazon 为内置保底不在此表。
7. **product_url 相对路径带 slug/ref**：`/Mayhoop-Stainless-Steel/dp/B093PZKKY8/ref=sr_1_1?dib=...` 前端点击会 404。**修复**：`_clean_product_url` 用 `re.search` 提取 `/dp/ASIN` 并转绝对 `https://www.amazon.com/dp/ASIN`（兼容 slug 前缀、绝对 URL、ref/sr= 追踪参数）。

### 解决方案要点

- **Amazon 工具**（`backend/app/core/agent/tools/amazon_bestsellers.py`）：搜索页人气排序主路径 + BSR url 兜底；USD cookie 强制；中英品类翻译；`bm-verify` 挑战检测；返回 `{ok, source:"amazon", query, items:[{rank, title, price, image_url, product_url, rating, reviews}]}`。

## 五、任务执行失败显示「❌ None」（DeepSeek tools 400，2026-08-19 晚）

### 背景需求

用户反馈：聊天页发「你好小娜帮我找一下北美戒指销量前10的商品」，确认执行后任务消息显示 **`❌ None`**，没有任何榜单结果。

### 问题与根因（两个独立缺陷）

1. **任务失败的根因——tools 参数格式不符**：`backend/app/core/agent/tools/registry.py` 的 `TOOLS` 数组元素为 `{"name", "description", "parameters"}`，缺 OpenAI 标准要求的 **`"type": "function"` 外层包装**。DeepSeek 官方端点严格反序列化校验，返回 HTTP 400：
   ```
   {"error":{"message":"Failed to deserialize the JSON body into the target type: tools[0]: missing field `type` at line 1 column 210","type":"invalid_request_error","param":null,"code":"invalid_request_error"}}
   ```
   已在容器内用用户实际模型 `deepseek-v4-flash` 实测对照：当前格式 + effort 参数 → 400；标准格式 + effort → 200；当前格式无 effort → 400；标准格式无 effort → 200——**`reasoning_effort` 与 tools 并不冲突，纯粹是 tools 缺 `type` 包装**。普通聊天不带 tools 所以一直正常，任务执行者带 tools 首次调用即 400（后端日志 `executor run failed: 模型服务返回错误（HTTP 400）…`）。
2. **「❌ None」的直接原因——workflow 异常路径漏 final_msg**：`workflow.py` 的 `except Exception` 分支把 `result` 置为失败 dict 后**直接 `break`**，跳过了下方 `if not result.get("success")` 里设置 `final_msg` 的分支，`final_msg` 保持初始值 `None`，会话留痕 `f"{status_icon} {final_msg}"` 写成 `❌ None`。
3. **诊断盲点**：`llm_provider.py` 把 HTTP 400 统一翻译成「请检查模型名与 API Key」，真实 detail（`missing field type`）被吞掉，这次排查全靠容器内最小请求重现才定位。

### 解决方案

1. **`registry.py`**：`_make_tools()` 返回的 spec 数组导出时包装为标准格式：
   ```python
   _SPECS, _HANDLERS = _make_tools()
   TOOLS = [{"type": "function", "function": spec} for spec in _SPECS]
   ```
   `call_tool` 分发仍按 `spec["name"]` 匹配，不受影响；Ollama / OpenAI 兼容端点均接受标准格式。executor 回填的 assistant 消息是 DeepSeek 返回的原始 message（含 `reasoning_content`），第二轮调用自动满足 DeepSeek 思考模式「带 tools 须回传 reasoning_content」要求，无需额外改动。
2. **`workflow.py`**：except 分支去掉 `break`，让流程落入下方统一失败处理（`final_msg = result.get("summary") or "任务执行失败。"`），并把真实错误拼进 summary（`执行出错：{e}`）。
3. **`llm_provider.py`**：新增模块级 `_raise_model_http_error(e, messages)` 供 `chat`/`chat_stream`/`chat_with_tools` 三处共用——仍先判带图 4xx → `VisionNotSupportedError`，其余把响应体真实 detail 记日志（`logger.warning`）并拼进用户文案（`模型服务返回错误（HTTP 400）：{detail}`），不再统一吞成「请检查模型名与 API Key」。

### 验证结论

- `python -m compileall -q backend/app` 通过。
- 容器内最小请求重现（DeepSeek `deepseek-v4-flash`）：4 组对照确认 tools 标准格式修复方向。
- 重建后端容器后端到端验证：发「北美银戒指销量前 10」→ 确认执行 → 任务完成显示 `✅` + 商品 Markdown 表格（图片/链接可看可点），不再出现 `❌ None`。
