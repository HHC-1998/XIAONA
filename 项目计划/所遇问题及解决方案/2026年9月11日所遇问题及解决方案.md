# 2026年9月11日所遇问题及解决方案

## 一、仓库从未初始化 git，无 .gitignore：.env 真实密钥面临泄露风险（推送前清理）

### 问题现象

用户打算把项目推送到 GitHub，要求先做一次「代码干净度」体检：哪些该 ignore、哪些是冗余可删。扫描后发现当前目录**既不是 git 仓库、也没有 `.gitignore`**——一旦直接 `git init && git add .`，`.env` 里的真实凭据会原样进入首个提交。

### 根因分析

1. **无 `.gitignore`**：仓库从未初始化 git（`git rev-parse` 报 `not a git repository`），自然也没建忽略规则，`.env` 与构建产物都处于「可被 add」状态；
2. **`.env` 是真实值而非占位符**：实测 `DB_PASSWORD`(11)、`NEO4J_USER`(5)、`NEO4J_PASSWORD`(11)、`FEISHU_APP_ID`(20)、`FEISHU_APP_SECRET`(32)、`FEISHU_VERIFY_TOKEN`(32)、`FEISHU_ENCRYPT_KEY`(32)、`FEISHU_BOT_OPEN_ID`(35) 均为真实凭据（仅 `OPENAI_API_KEY` 为空）；
3. **冗余堆积**：
   - `XIAONA/`（嵌套目录）内含**孤儿 git 仓库** `XIAONA/.git`——只有 1 个 commit `2de8100 Initial commit`、无 remote、`git ls-files` 仅一个 `.gitattributes`（LF 归一化模板）。留着会让外层仓库把它当嵌套仓库/submodule 处理；
   - `backend/xiaona.db` 155 KB 陈旧 SQLite（PostgreSQL 迁移前遗留），全仓 **0 处引用**；表内除 `data_source_configs` 3 行测试夹具（`user-a`/`user-b`、`etsy-k...`、`key-x`）外全为空；
   - `plan_extract.txt` 8.2 KB 临时提取稿；
   - 9 个 `__pycache__/`（含 `cli/__pycache__/xiaona.cpython-314.pyc`）；
   - 体积大头 `frontend/node_modules` **125.7 MB**、`frontend/dist` 1.8 MB。
4. **源码本身干净**：全仓扫描（*.py/*.js/*.jsx/*.yml/*.json/*.md/*.txt/*.conf，排除 node_modules/dist/__pycache__）**未发现**硬编码 `sk-`/`AKIA`/`ghp_`/私钥或字面量密码。

### 解决方案

**1. 新建根级 `.gitignore`**（此前不存在），分组覆盖：
- 密钥类：`.env` / `.env.local` / `.env.*.local`，并用 `!.env.example` **显式豁免**示例文件——**不可写成 `.env*`**，否则会把需要提交的 `.env.example` 一起挡掉；
- Python：`__pycache__/`、`*.py[cod]`、`*.egg-info/`、`.venv/`、`venv/`；
- 前端：`node_modules/`、`frontend/dist/`（dist 由 `frontend/Dockerfile` 构建阶段 `npm run build` 重建，`start.py` 只走 `docker compose up --build`，不读本地 dist）；
- 运行时产物：`artifacts/`、`backups/`（artifacts 为 compose bind mount，见 AGENTS.md「产物落盘」）；
- 数据库/日志：`*.db`、`*.sqlite`、`*.sqlite3`、`*.log`；
- 系统/编辑器：`.DS_Store`、`Thumbs.db`、`desktop.ini`、`.idea/`、`.vscode/`、`*.swp`。

**2. 删除冗余文件**（详见下表），**artifacts/ 下 7 个产物仅忽略不删**（含 `SRR系统香港本地化部署方案.docx` 等实测产物，仍有对照价值）。

**3. 决策**：用户确认仓库为**私有**，因此 `项目计划/` 26 份文档（含 SRR 客户报价/HKD 金额明细）全部保留随仓推送；本次**只写 .gitignore + 删冗余**，暂不执行 `git init`。

### 改动文件清单

- 新增 `/.gitignore`（根级忽略规则）
- 删除 `XIAONA/`（孤儿嵌套 git 仓库，仅含 `.gitattributes`）
- 删除 `backend/xiaona.db`（陈旧 SQLite，0 引用）
- 删除 `plan_extract.txt`（临时提取稿）
- 删除 9 个 `__pycache__/` 目录

### 验证结论

静态核对通过（按 AGENTS.md 约定不代跑构建、不做容器实测）：

- 待推送清单从 133 → **129 个文件 / 1.85 MB**（backend 57、frontend 41、项目计划 26、cli 2，加 `.env.example`/`AGENTS.md`/`start.py`），与计划预估完全吻合；

## 二、推送到 GitHub 私有库 HHC-1998/XIAONA（README + git init + 安全闸 + rebase 冲突）

### 问题现象

在完成一节的清理后，用户要求把项目首次推送到 GitHub 私有库 `HHC-1998/XIAONA`。执行过程中出现两个非预期情况：

1. 首次 `git push -u origin main` 被拒绝：
   ```
   ! [rejected]  main -> main (fetch first)
   error: failed to push some refs to 'https://github.com/HHC-1998/XIAONA.git'
   ```
2. `git fetch` 后发现远端**已有一个提交** `2de8100 Initial commit`，其 `git ls-tree` **只有一个文件 `.gitattributes`**。

### 根因分析

1. **远端并非空库**：用户此前已在 GitHub 建过该私有库，并勾选了 GitHub 新建仓库页面的 `.gitattributes` 模板选项，因此远端存在一个只含该文件的初始提交。**这不是认证失败**——能读到 `refs/heads/main` 说明凭据是通的，只是本地与远端历史无关（unrelated histories）。
2. **被删的孤儿仓库就是该远端的残留克隆**：一节中删除的 `XIAONA/.git` 里那个唯一提交 `2de8100 Initial commit` 与远端 **commit hash 完全一致**、文件清单也一致（仅 `.gitattributes`）。即 `XIAONA/` 是该仓库的旧克隆残留，删除它**没有丢失任何远端没有的内容**——一节的删除决策被反证为安全。
3. **`.gitattributes` 必然冲突**：本地新建的 `.gitattributes`（LF 归一化 + `.sh eol=lf` + 二进制白名单）与远端那份 stock 模板是「双方各自新增同一路径」，rebase 时构成 `add/add` 冲突。
4. **认证无需额外操作**：全局 `credential.helper=manager`（GCM 2.9.0）已持有可用凭据，**首次 push 并未弹出浏览器登录**（计划中预留的「需用户手动登录」环节实际未触发）。

### 解决方案

**1. 新建 `README.md`**（中英双语，中文为主、顶部英文简介）：项目简介 / 功能特性（单 Agent 聊天、三层记忆、知识图谱、实时语音、桌面助手、飞书机器人、CLI、多类型文件上传、多 Agent 任务）/ 技术栈表 / 快速开始 / 访问入口 / 目录结构 / 文档入口 / 安全提示。

**2. 新建 `.gitattributes`**：`* text=auto` + `*.sh text eol=lf` + 图片/PDF/Office/DB 二进制白名单。本机 `core.autocrlf=true` 只是本地设置，提交该文件可让任何克隆端行为一致（Windows 开发 + Linux 容器组合尤其需要）。

**3. `git init -b main`**（显式指定 `main`，因 `init.defaultBranch` 未设置）。

**4. 提交前安全闸（`git add -A` 后硬断言，不通过即中止）**：
- 逐项断言 `.env` / `node_modules` / `frontend/dist` / `artifacts/` / `*.db` / `*.sqlite` / `__pycache__` / `*.pyc` / `*.log` 在 `git ls-files` 中命中数**必须为 0** → 实测全部 `hits=0`；
- 另用 `git check-ignore -v` 反向确认忽略规则生效位置：`.env` → `.gitignore:2`、`node_modules/` → `.gitignore:15`、`frontend/dist/` → `.gitignore:16`；
- 断言 `.env.example` / `.gitignore` / `.gitattributes` / `README.md` / `AGENTS.md` / `start.py` 等**必须**已纳入 → 全部 `tracked=True`。

**5. 提交用 UTF-8 消息文件而非命令行内联**：`git commit -F "$env:TEMP\xiaona_commit_msg.txt"`。中文 + em dash 直接写在 PowerShell 命令行里会被按 ANSI 重新编码而乱码，写文件再 `-F` 可保证提交消息 UTF-8 正确（该临时文件位于仓库外，用完即删）。

**6. push 被拒后按计划改走 `git pull --rebase`**（非破坏性，保留远端提交）：
- `git rebase origin/main` → 仅 `.gitattributes` 一个 `add/add` 冲突；
- 用 `git checkout --theirs -- .gitattributes` 取**本地版本**——**rebase 中 `ours`/`theirs` 是反的**：`ours` 指已重放到的上游（远端那份 stock 模板），`theirs` 才是被重放的工作分支提交（本地这份超集），取错会丢掉 `.sh eol=lf` 与二进制白名单；
- `git add` 后 `git -c core.editor=true rebase --continue`（`core.editor=true` 免编辑器挂起）；
- 未使用 `--force-with-lease`——非破坏性路径即可解决，无需破坏远端历史。

### 改动文件清单

- 新增 `/README.md`（中英双语项目说明）
- 新增 `/.gitattributes`（换行归一化 + 二进制白名单）
- 新增本节文档（追加到 `2026年9月11日所遇问题及解决方案.md`）
- 本地仓库：`git init -b main`，首个提交 `1b06d27`（rebase 后），远端 `origin` = `https://github.com/HHC-1998/XIAONA.git`

### 验证结论

静态检查通过（按 AGENTS.md 约定不代跑构建、不做容器实测）：

- **推送成功**：`2de8100..1b06d27  main -> main`，`branch 'main' set up to track 'origin/main'`；
- **本地与远端一致**：`git rev-parse main` 与 `git rev-parse origin/main` 均为 `1b06d274b30ebd1b325e29588d2f3dbf3412ded7`；`git ls-remote origin` 输出 `refs/heads/main` 同一 SHA，确认确实到达远端；
- **`git status -sb` = `## main...origin/main`** 且 `git status --porcelain` 为空（工作区干净、无未提交改动）；
- **推送前对 `HEAD` 树做终检**：`git ls-tree -r --name-only HEAD` 共 **133 个文件**，`.env` / `node_modules` / `frontend/dist` / `artifacts/` / `*.db` / `__pycache__` / `*.pyc` 命中数**全为 0**；`git ls-files | ? {$_ -eq '.env'}` 判定 **SAFE: .env is NOT tracked**；
- **文件数对账**：一节清理后为 129，后续新增 `2026年9月11日…md`(+1)、`README.md`(+1)、`.gitattributes`(+1)、`.gitignore`(+1) = **133**，与提交统计 `133 files changed, 34783 insertions(+)` 吻合；
- 提交历史：`1b06d27`（本项目初始提交）← `2de8100 Initial commit`（远端原有，已保留在历史中）。

### 遗留提醒
