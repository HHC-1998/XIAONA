# 2026年8月15日 所遇问题及解决方案

> 本目录按日期归档 XIAONA 开发过程中遇到的问题与解决方案，作为项目问题台账。当日所有代码修改、排查结论均反哺至此，同时同步更新到对应的原计划文档。

## 一、登录/注册成功后无法跳入内部页面

### 问题现象

点击登录（密码登录或验证码登录）后，页面闪回登录页，无法进入聊天内部页面；注册成功后同样无法进入。

### 根因分析

`frontend/src/pages/Login.jsx` 与 `Register.jsx` 登录成功后只执行 `localStorage.setItem('token', res.token)`，**没有更新 `AuthContext` 中的全局 `user` 状态**。而 `/` 路由受 `AuthRoute` 保护：

```jsx
// frontend/src/components/AuthRoute.jsx
return user ? children : <Navigate to="/login" replace />;
```

`user` 仍为 `null`，于是刚跳转到 `/` 就被 `<Navigate to="/login">` 弹回登录页，形成"登录后无法进入内部页面"的假象。后端 `/api/auth/login` 与 `/api/auth/register` 实际已返回 `{ token, user }`（`_user_dict` 含 id/phone/nickname），前端只是没用上 `user` 字段。

### 解决方案

在 `AuthContext` 中新增统一的 `login(token, user)` 方法（写 localStorage + setUser），登录/注册成功后调用它再跳转：

```jsx
// frontend/src/contexts/AuthContext.jsx
const login = (token, user) => {
  localStorage.setItem('token', token);
  setUser(user);
};
```

```jsx
// frontend/src/pages/Login.jsx（Register.jsx 同理）
const { login } = useAuth();
const res = await authApi.login({ phone, password });
login(res.token, res.user);
navigate('/');
```

### 经验总结

- 认证状态必须单一来源（`AuthContext`），登录/注册/绑定手机号都通过它写入全局状态，避免只写 localStorage 导致的路由守卫误判。
- 路由守卫（`AuthRoute`）依赖全局 `user` 判断登录态，任何"写 token 但不写 user"的登录路径都会踩此坑。

## 二、聊天界面没有删除会话功能

### 问题现象

聊天侧边栏的会话只能创建、点击打开，无法删除。

### 现状分析

后端能力已具备：`DELETE /api/sessions/{id}`（body 传 `{"password": "..."}`，三层存储清理，见 07 §9），前端 `sessionsApi.remove(id, password)` 也已封装，**缺的是 UI 入口**。

### 解决方案

1. **`DeleteConfirm` 组件通用化**：原组件文案固定为"确认清空数据"，新增可选 props `title` / `description` / `confirmText`，默认值保持原样，`Settings.jsx` 数据管理区调用不受影响。
2. **聊天侧边栏加删除入口**：每个会话项 hover 显示 `×` 删除按钮（`stopPropagation` 防止误触切换会话），点击弹出密码确认框；确认后调用 `sessionsApi.remove` 并从列表移除；若删除的是当前会话，同时清空 `sessionId` 与 `messages`。

## 七、聊天中删除会话改为免密软删除（数据保留在三库）

### 需求背景

用户要求：聊天界面删除会话**不需要密码**；删除后**不是真删**——SQL / Chroma / 知识图谱三层数据全部保留，仅从界面与历史会话隐藏，后续记忆检索与模型思考仍能调用。设置页「清空数据」仍保持需密码的硬删除。

### 实现方案

1. **数据模型**（`backend/app/db/sql_models.py`）：`Session` 新增 `is_deleted = Column(Boolean, default=False)`。
2. **轻量迁移**（`backend/app/db/database.py`）：`create_all` 不会给已存在的表补新列，`init_db()` 增加 `_apply_light_migrations()`——`inspect` 检查 `sessions` 缺 `is_deleted` 列时执行 `ALTER TABLE sessions ADD COLUMN is_deleted BOOLEAN DEFAULT FALSE`（兼容 SQLite/PostgreSQL）。
3. **删除接口改免密软删除**（`backend/app/api/sessions.py`）：`DELETE /{session_id}` 移除密码校验，仅 `session.is_deleted = True; db.commit()`，**不再**清理 SQL/Chroma/KG（原来调用的 `chroma.delete_session` / `neo4j_client.delete_or_soft_delete_session_refs` 均移除）。
4. **查询接口过滤**：`list_sessions` / `search_sessions` / `get_session` / `get_session_messages` / `export_session` / `rename_session` 全部加 `is_deleted=False` 过滤；`memory_engine.ensure_session` / `get_all_sessions_with_messages` 同样过滤，避免软删会话被继续写入"复活"。
5. **前端**（`DeleteConfirm.jsx`）：新增 `requirePassword` prop（默认 `true`），`false` 时不显示密码输入框、`onConfirm` 不传参；`Chat.jsx` 删除会话改用 `requirePassword={false}`，`sessionsApi.remove(target.id)` 不再传密码。

### 验证

- 注册新账号 → 创建会话 → `DELETE /api/sessions/{id}`（无 body）返回 `{ok:true, soft_deleted:true}` → 列表不再出现该会话 → psql 查询 `sessions` 表该行 `is_deleted=t` 且记录仍在（数据保留）。

## 八、知识图谱注册即建自我节点 + 3d-force-graph 白底风格

### 需求背景

用户要求：新用户注册时图谱至少有"自我节点"（名称=昵称，未设置昵称则"用户+手机号"）；图谱风格参照 `vasturiano/3d-force-graph`，**白色背景**。

### 实现方案

1. **`ensure_self_node`**（`backend/app/db/neo4j_client.py`）：按 `{user_id, is_self: true}` 幂等 MERGE 一个 `Person` 节点，设置 `is_self: True`；`ON CREATE` 设名称与别名，`ON MATCH` 更新名称（昵称变更后自动同步）。
2. **触发时机**（`backend/app/api/auth.py`）：`register` 提交后调用 `neo4j_client.ensure_self_node(user.id, user.nickname)`，`try/except` 容错（Neo4j 未就绪不阻断注册）；`login` 时兜底再调用一次。
3. **孤立节点可显示**（`neo4j_client.get_full_graph`）：原查询只返回有关系的节点对，新注册用户的自我节点无关系 → 不在结果中。新增 `orphan_query`（`WHERE NOT (n)--()`）把所有孤立节点并入返回，保证新用户图谱至少有自我节点一个点。
4. **前端风格**（`frontend/src/components/Graph3D.jsx`）：白底保留，增强为 3d-force-graph 官方风格——hover 节点放大（`onNodeHover` 调 `__threeObj.scale`）+ `nodeLabel` 显示标签、节点彩色半透明球（`nodeOpacity`）、自转/拖拽/缩放、`nodeVal` 按度数定大小；自我节点（`properties.is_self`）用 `nodeThreeObject` 自定义**渐变发光球**高亮（THREE 半透明外层 + 高亮内核）。`three` 为 3d-force-graph 的直接依赖，可直接 `import * as THREE from 'three'`，无需新增依赖。

### 验证

- 无昵称注册新账号 → `GET /api/memory/graph` 返回 1 个节点：`label=Person`、`properties.is_self=True`、`name=用户{手机号}`；Neo4j 内确认 `is_self=true` 节点存在。

## 九、桌面助手问答归档到固定会话并写入三库

### 需求背景

用户要求：桌面助手语音问答也要进入 SQL/Chroma/知识图谱三库，供模型后期更好思考。

### 现状分析

`memory_engine.chat()` 的 `_persist()` 已写 SQL+Chroma+KG，但桌面助手页 `chatApi.send(text)` **未传 `session_id`**，后端 `ensure_session` 每次新建会话，造成大量碎片化空会话。

### 实现方案

1. **前端固定会话**（`frontend/src/pages/DesktopAssistant.jsx`）：`localStorage` 存 `desktop_session_id`，无则 `sessionsApi.create('desktop')` 创建并复用；`chatApi.send(text, sessionIdRef.current)` 传入。
2. **后端返回实际会话 id**（`backend/app/api/chat.py` + `memory_engine.chat`）：`POST /api/chat` 返回 `{reply, session_id}`（`ensure_session` 可能自愈新建），前端据此同步 localStorage，避免碎片化。
3. `sessionsApi.create` 支持 `source` 参数（`create(source='web')`），桌面助手传 `'desktop'`。

### 验证

- `POST /api/sessions`（`source=desktop`）创建成功，会话列表可见；会话 id 存 localStorage 后复用。

## 十二、关系网空白：旧账号图谱没有任何节点

### 问题现象

用户反馈：纯新账号（没聊过天）打开关系网界面是**空白**，连自己的自我节点都看不到。

### 根因分析

`get_full_graph` 只做读取，自我节点只在 `register`/`login` 时兜底创建。若账号注册于自我节点功能上线之前，且期间没有重新登录触发 login 兜底，则该用户 `user_id` 在 Neo4j 中不存在任何节点 → 图谱接口返回空数组 → 前端空白。此外 `get_full_graph` 的孤立节点查询只在有节点时才有效。

### 解决方案

`backend/app/api/memory.py` 的 `GET /api/memory/graph` 在查询前**兜底调用 `ensure_self_node(user.id, user.nickname)`**（try/except 容错，Neo4j 未就绪不阻断、前端展示空态提示）。这样无论新账号还是功能上线前的旧账号，打开图谱页都至少有 1 个自我节点。

### 验证

- 容器内 TestClient 实测：新注册账号 → graph 返回 1 节点（Person、is_self=True）。
- 清空某用户 Neo4j 节点后再次调用 graph → 兜底补建自我节点，仍返回 1 节点。

## 十三、关系网页面有上下/左右滚动条，图不满屏

### 问题现象

用户反馈：关系网打开后右侧和下方出现滚动条，且 3D 图不随屏幕大小自适应；期望图的大小用**滚轮缩放**控制（3D 相机），而不是调整页面滚动条。

### 根因分析

`App.jsx` 的 `<main>` 是 `flex-1 overflow-auto`，`Graph.jsx` 顶层用 `h-full`，而 `ForceGraph3D` 内部 canvas 尺寸按首次挂载时的容器推算，容器高度链路不稳导致 canvas 溢出 → main 出现滚动条。

### 解决方案

- `App.jsx`：`<main>` 加 `relative`（其他页面仍可滚动，仅关系网页占满可视区）。
- `Graph.jsx`：顶层改为 `absolute inset-0 bg-white`（严格等于 main 可视区），用 `containerRef` + `useLayoutEffect` + `ResizeObserver` 量取容器真实宽高存入 state，显式传给 `<Graph3D width height>`。
- `Graph3D.jsx`：接收 `width`/`height` 传给 `<ForceGraph3D>`；空数据时显示居中空态提示（"图谱还没有节点，先和 XIAONA 聊几句吧"）；自我节点球体略微放大（halo 4.2 / core 3.0）单节点时更醒目。

## 十四、桌面助手需要手动点开始/停止监听

### 问题现象

用户反馈：不希望手动点击"开始监听/关闭监听"，期望**打开桌面助手页面就自动监听，切换到其他页面就自动停止**。

### 根因分析

### 解决方案

- 移除手动开始/停止按钮，页面只保留状态圆环与状态文字（"监听中/已停止"）。
- 新增 `suppressRef`：TTS 播放开始置 `true`、结束恢复；`checkVolume` 循环顶部检测到 `suppressRef.current` 直接跳过音量处理，真正屏蔽回声误识别。
- 新增 `audioRef` 保存播放中的 `Audio`，`stopListening`（组件卸载）时 `pause()` 中断回复。
- 麦克风权限被拒时自动重试一次并友好提示。

## 十七、聊天框语音输入不能边说边显示

### 问题现象

用户反馈：聊天框的语音输入好用，但必须"点语音 → 说一段话 → 再点结束"才把整段文字显示到输入框；希望**点击开始后说话，文字边说边实时流入输入框**，且**点击输入框/页面别处/切换到别的界面时话筒自动关闭**。

### 根因分析

原 `VoiceRecorder` 用 `MediaRecorder` 整段录音，停止后才把 Blob 上传 `/api/voice/transcribe`（后端 Whisper 一次性转写整段音频），因此必须"点结束才出字"；也没有"点击别处自动停止"的交互。

### 解决方案

改用**浏览器原生 Web Speech API**（`webkitSpeechRecognition`）为主路径，它原生支持 `interimResults`（边说边逐字出字）与 `continuous`，且是浏览器内置能力、零后端改动：

## 十八、设置页所有厂商的 Base URL 都残留 OpenAI 地址

### 问题现象

用户反馈：选择厂商后想让 Base URL 自动换成该厂商的默认地址，结果不管选哪个厂商，URL 都是 OpenAI 的，甚至给所有模型都填了 OpenAI 的 URL。

### 根因分析

`Settings.jsx` provider 切换逻辑写的是 `base_url: newModel.base_url || info?.defaultBaseUrl || ''`——一旦 `base_url` 里已有值（初始默认就是 OpenAI 地址，或用户切过一次厂商已填值），`||` 短路导致永远取旧值，切到任何厂商都不会替换成新厂商的默认 URL。

### 解决方案

- 新增 `baseUrlTouched` 标志（默认 `false`）：Base URL 输入框 `onChange` 置 `true`（用户手动改过 URL）。
- provider 切换时：`!baseUrlTouched` 则 `base_url` **直接覆盖**为所选厂商默认地址（`info?.defaultBaseUrl || ''`）；已手动改过则保留用户输入；切到 custom 保留当前值。
- `openEdit`/打开表单/取消/保存成功时重置 `baseUrlTouched=false`，保证"添加模型"场景切厂商即换 URL、编辑场景以模型原值为主。

## 十九、扫描模型应是自动下拉列表而非手动点按钮

### 问题现象

用户反馈：添加模型时不应该让用户手动点「扫描模型」按钮，而是选了厂商后（如 Ollama）就**自动扫描**本地/该端点已装的模型，模型名直接变成**下拉列表**让用户选择，而不是手输。

### 根因分析

## 二十、桌面助手思考/回复期间无法打断

### 问题现象

用户反馈：桌面助手对话应是"用户说完 → 模型思考 → 回复"全程可被打断——模型思考或说话时用户再说新话，应立即停止并转听新语音、基于新语音重新生成，而不是等整段回复播完；同时单轮思考+回复时间要短，不能让用户等太久。

### 根因分析

上一版用 `suppressRef` 在 TTS 播放期间**完全屏蔽** VAD 音量处理，用户说话根本不会被听到，无法打断；也没有思考期间的打断机制。

### 解决方案

- 新增 `genRef`（代际计数器）与 `busyRef`（思考/回复中标志）；保留 `suppressRef` 仅作为"TTS 播放中"标志，不再用于屏蔽监听。
- `checkVolume`：`busyRef || suppressRef` 时不 return，而是持续检测——思考期间阈值 30、TTS 播放期间阈值提高到 60（无 AEC 时降低把回复回声误判为用户语音的概率），超过即 `interrupt()`。
- `interrupt()`：`genRef+1` 令在途 `processVoice` 过期、`audioRef.pause()` 立即停播回复、`busyRef/suppressRef` 复位、若未录音则立即 `recorder.start()` 录新语音，状态置"听到你了，请说..."。
- `processVoice`：开头记录 `gen = genRef.current`，每个 `await`（transcribe/chat/tts）后校验 `gen === genRef.current && aliveRef.current`，不满足则丢弃（已发后端的对话照常落库，只是前端不播放旧回复）。
- 思考期间 `busyRef=true`、播放期间 `suppressRef=true`；`onended`/播放失败/出错/`stopListening` 均复位。
- "回复时间短"：打断后交互等待只取决于单轮生成；用户可为聊天功能分配响应更快的模型（后端超时配置不变）。

4. **不动**：`list_models`（扫描）保持 8s 短超时（`GET /api/tags` 即时返回）；前端 `ModelCard.jsx` / `settings.js`、docker-compose、nginx 均不改。

## 二十七、三模型独立弹性配置：对话模型必须 / 提炼、向量化可选门控

### 问题现象

## 二十八、会话"丢失"与持久化链路修复

### 问题现象

聊天后切走页面再回来，对话消失；新建会话后点旧会话、再点回新会话，新会话内容丢失。

### 根因分析

1. 此前 chat 链路在检索/生成阶段失败（如二十六的 embedding OSError）时 `_persist` 未执行，**消息从未落库**。
2. `Chat.jsx` 的 `sessionId` 只在内存 state，**不同步 URL**，刷新/切回即丢活动会话。
3. 用户消息仅在 LLM 成功后才一并落库，失败即丢失。

### 解决方案

1. **用户消息先行落库**（`memory_engine`）：拆分为 `_persist_user`（LLM 调用前执行，`chat_stream` 在 `yield` 前、`chat` 在调 LLM 前调用）+ `_persist_reply`（流结束后 finally 执行）。LLM 失败/中断，用户说的话也已在三库。
2. **URL 同步**（`Chat.jsx`）：`setSearchParams({ session_id })`（replace 模式），刷新/返回可恢复当前会话。
3. **无会话先建再发**：`sendMessage` 里 `sessionId` 为空时先 `sessionsApi.create()` 拿到真实 id 再发送，避免后端自愈新建导致前端 sessionId 失联。
4. **SSE 首帧回传实际 session_id**（`chat.py`）：`event_stream` 开头 `ensure_session` 后首帧 `data: {"session_id": "..."}`；桌面助手固定会话软删后据此同步最新 id（防碎片化），前端 `streamChat` 支持 `onSession` 回调。
5. **流结束刷新会话列表**：`finish()` 后 `sessionsApi.list()` 重拉侧边栏，标题自动更新后立即可见。

## 三十三、聊天回复"一次性输出"而非流式 → 前端打字机逐字流式

**问题现象**：已实现 SSE 流式，但用户反馈聊天回复是"统一输出"（一次性整段出现），没有打字机逐字浮现的平滑感；思考过程倒是实时。

**根因分析**：
1. `streamChat` 在单次 `reader.read()` 返回后**同步循环**解析全部 SSE 帧；若一次网络读取拿到多帧（DeepSeek `deepseek-v4-flash` 最终 `content` 一次性返回；浏览器缓冲合并帧），多次 `onDelta` 在同一 JS tick 内同步触发 → React 18 自动批处理只渲染一次；
2. 即使逐帧到达，浏览器 rAF 节流也会合并显示，肉眼仍是"整段出现"。

**解决方案**：在 `Chat.jsx` 本地实现 reveal 队列（打字机）：
- `pendingRef`（待显示 content 队列）+ `revealTimerRef`（30ms 定时器）；
- `onDelta` 只把增量 push 进队列，定时器每 tick 揭晓 ~3 字符后 `patchAssistant`，各 tick 是独立宏任务 → 逐字平滑浮现，与网络/模型时序彻底解耦；
- `finish()` / 流中断 / 切换会话（`abortRef.abort` + `clearReveal`）清空队列并补全剩余内容，防止写旧消息；
- thinking 保持即时直通，不做队列。

**改动文件**：`frontend/src/pages/Chat.jsx`（新增 `pendingRef/revealTimerRef/clearReveal`，`sendMessage` 内 `startReveal/flushPending`）。

## 三十四、桌面助手一直"已停止"、不听说话 → start/stop 竞态 + 权限错误静默

**问题现象**：桌面助手页打开后图标常驻"已停止"，不说话、不响应；偶尔能进"监听中"但切页/切标签后恢复又失败。

**根因分析**：`startListening` 的 `await getUserMedia` 挂起期间若发生 blur/切页（调 `stopListening`），stop 时 `streamRef` 仍为 null 只置状态；随后 start 的 await 恢复，把 `streamRef` 赋值并 `setIsListening(true)`，**覆盖 stop 状态**，组件卸载后仍创建 MediaStream **泄漏占用麦克风**；权限被拒 / `AudioContext` 异常也静默停在"已停止"。

**解决方案**（`frontend/src/pages/DesktopAssistant.jsx`）：
- 新增 `startGenRef` 代际计数：`startListening` 开头 `const gen = ++startGenRef.current`；`await getUserMedia` 之后校验 `gen !== startGenRef.current || !aliveRef.current` → 立即 `stream.getTracks().forEach(t => t.stop())` 并 return；`stopListening` 开头 `startGenRef.current++` 令在途 start 全部失效；
- `startListening` 整体 try/catch + `describeMicError` 分类：`NotAllowedError`→「权限被拒，点地址栏锁图标」、`NotFoundError`→「未检测到麦克风设备」、`NotReadableError`→「被其他应用占用」、其余→具体 message；
- `new AudioContext()` 包 try/catch（极罕见失败归类为启动失败并释放流）；
- 启动失败渲染区出现「重新启动监听」按钮（点 `startListening`），不再只能刷新页面。

## 三十八、新会话发消息丢失（SSE 499 断流，需二次点击才保留）

**问题现象**：新会话状态下直接发消息，屏幕闪一下、侧边栏新建了会话，但刚发的内容全丢了；点进新会话重发一次才保留。

**根因分析**：无会话时 `sendMessage` 内部先 `sessionsApi.create()` 拿到真实 id，再 `setSessionId(sid)`。该 `setSessionId` 触发两个依赖 `sessionId` 的 effect：① reload effect 用 `GET /api/sessions/{id}` 拉新会话的空消息列表，**覆盖**了刚 append 的乐观消息；② 卸载 effect 直接 `abortRef.current?.abort()`，**中断**刚发起的 SSE 流——后端日志 `POST /api/chat/stream 499`（客户端在响应前关闭连接）就是直接证据。

**解决方案**（`frontend/src/pages/Chat.jsx`）：引入两个**一次性守卫 ref**：
- `pendingSendRef`：reload effect 内 `if (sessionId && !pendingSendRef.current)` 才拉消息，懒创建放行后只刷新会话列表不覆盖乐观消息；
- `noAbortRef`：卸载 effect 内 `const skipAbort = noAbortRef.current; noAbortRef.current = false; if (!skipAbort) abortRef.current?.abort()`，放行本轮不中断刚发起的流；
- 两个标记都在懒创建分支 `setSessionId(sid)` 前置位，一次性消费后复位，其余路径（点侧边栏切会话、点「+ 新会话」）行为不变。

## 三十九、聊天页麦克风不能边说边出字（Web Speech 网络失败不降级）

**根因分析**：Chrome 的 `webkitSpeechRecognition` 依赖 Google 服务，网络受限时 `onerror` 报 `network` 直接停止且不降级；`start()` 抛错（连续 start 被浏览器拒绝）也只报错。旧版降级路径 `startMediaRecorder` 只在**手动停止后**才上传整段音频转写，做不到"边说边出字"。

**解决方案**（`frontend/src/components/VoiceRecorder.jsx` 重写）：
- **主路径不变**：Web Speech API（`continuous + interimResults`）实时回调全文；
- **network / service-not-allowed / audio-capture 错误自动降级**：切到 MediaRecorder + 后端 Whisper，不再中断体验；

- `aliveRef` 卸载保护：组件卸载后 `onstop` 转写回调不再刷新输入框（防 setState-on-unmounted）；
- 权限/设备错误仍分类提示（NotAllowed→锁图标、NotFound→无设备、NotReadable→被占用）。

> **配套后端修复（本次新增）**：聊天/桌面助手转写都走后端 `/api/voice/transcribe`，但容器内 `faster-whisper` 模型未预下载且无法访问 huggingface.co，`_build_asr()` 初始化失败被静默吞掉 → 转写抛 `NotImplementedError`（日志见 `raise NotImplementedError`）。修复：`backend/Dockerfile` 构建阶段预下载 `Systran/faster-whisper-base`（走 Clash 代理）；`asr_provider.py` 空实现返回空字符串（不再抛 500）+ 初始化失败打日志。详见下文「四十六」。

## 四十、桌面助手打开一直「已停止监听」（AudioContext 挂起致 VAD 恒 0）

**问题现象**：桌面助手页一打开就显示「已停止监听」，不监听、不响应。注：`三十四` 已修 start/stop 竞态与权限错误静默，本项是其后的**第二层根因**。

**根因分析**：浏览器自动播放策略下无用户手势直接 `new AudioContext()` 状态为 `suspended`，`AnalyserNode.getByteFrequencyData` 恒返回 0 → VAD 永远判定"无音量"→ 录音不开始、状态停在「已停止监听」。

**解决方案**（`frontend/src/pages/DesktopAssistant.jsx`）：

- `setupVAD` 的 `checkVolume` 每帧开头兜底 `resume()`（防某些浏览器手势丢失后 AudioContext 被再次挂起）。

## 四十一、Ollama 本地模型在设置页无法连接（容器内 localhost 指向容器自身）

**问题现象**：设置页云端模型都能连通，唯独 Ollama 本地模型连不上。用户诉求：**不改 Docker 路径，填 `localhost:端口` 必须能连通**。

**根因分析**：后端跑在 Docker 容器内，`localhost` 指向容器自身而非宿主机；宿主机上 Ollama 监听 `localhost:11434`，容器内请求自然失败。

**解决方案**（`backend/app/core/llm_provider.py` + `backend/docker-compose.yml`）：
- `_in_docker()`（`XIAONA_IN_DOCKER=1` 标记）+ `_resolve_host(base_url)`：容器内把 `localhost / 127.0.0.1 / 0.0.0.0` 自动翻译为 `host.docker.internal`，再走 `_ensure_v1` 与 `list_models`（`/api/tags` 扫描）与连通性测试；容器外运行不翻译；
- compose 的 backend 服务新增 `XIAONA_IN_DOCKER: "1"` 与 `extra_hosts: ["host.docker.internal:host-gateway"]`（Linux 主机也解析到宿主机）；

## 四十七、桌面助手打开一直「已停止监听」：setupVAD 先于 MediaRecorder 初始化

**问题现象**：桌面助手页打开后圆形图标一直是「已停止」、状态栏「已停止监听」，不说话不对话不语音输出。注：`四十` 已修 AudioContext 挂起，本项是其后的**第三层根因**（代码级确认）。

**根因分析**（`frontend/src/pages/DesktopAssistant.jsx`）：`startListening` 中 `setupVAD(source)` 被调用在 `mediaRecorderRef.current = recorder` **之前**，而 `setupVAD` 末尾会**同步执行一次** `checkVolume()`，其中 `mediaRecorderRef.current.state` 此时为 `null` → 抛 `TypeError: Cannot read properties of null (reading 'state')` → 异常中断整个 `startListening`，`setIsListening(true)`/`setStatus('正在监听...')` 永不执行、VAD rAF 循环永不调度。即打开页面即崩溃。

**解决方案**：
1. **调整顺序**：先创建 `MediaRecorder`、绑定 `ondataavailable/onstop`、赋值 `mediaRecorderRef.current = recorder`，**之后**再调用 `setupVAD(source)`；
2. **整段 try/catch**：建 AudioContext → 建 recorder → setupVAD 任一步失败都停流释放 + `setMicError` + 渲染「重新启动监听」按钮，不留静默死状态；
3. **checkVolume 空指针防护**：`mediaRecorderRef.current` 为 null 时直接 `rafIdRef.current = requestAnimationFrame(checkVolume); return;`；
4. **AudioContext 用户激活兜底**：`getUserMedia` 权限弹窗可能耗尽浏览器"用户激活"窗口（约 5s）致 `await resume()` 静默失败（context 仍 suspended → 音量恒 0 → 听不到）；注册一次性 `document` `pointerdown/keydown` 监听器，用户下次点击页面时 `resume()` 并自移除（`stopListening`/卸载时移除，防泄漏）。

**改动文件清单**：`frontend/src/pages/DesktopAssistant.jsx`、`项目计划/01_单Agent聊天助手/08_桌面助手详解.md`、`05_前端详解.md`、`AGENTS.md`。

## 四十八、桌面助手「显示监听中但不响应说话」：VAD 数组尺寸稀释音量 + 频域阈值不灵敏

**问题现象**：桌面助手能正常显示「监听中」，但说话 9/10 不响应；偶发触发还只抓到半句话导致转写内容不对。用户确认麦克风硬件正常（其他软件语音可用）。

**根因分析**（`DesktopAssistant.jsx` 的 `setupVAD` 与 `VoiceRecorder.jsx` 的 `vadLoop` 同源）：
```js
const dataArray = new Uint8Array(analyser.fftSize);   // fftSize=2048 个元素
analyser.getByteFrequencyData(dataArray);             // 只填前 frequencyBinCount=1024 个
const volume = dataArray.reduce((a, b) => a + b) / dataArray.length;  // 除以 2048
```
- `getByteFrequencyData` 只写入前 `frequencyBinCount`（= fftSize/2 = 1024）个元素，后 1024 个恒为 0；
- `volume` 被除以 2048 → 真实平均被稀释一半 → **阈值 30 实际等效 60**，人声只有很响的发音才能越过；
- 频域平均 + 固定阈值对音量/环境噪声不鲁棒；VAD 晚触发抓到半句话 → 转写内容不对。

**解决方案**：
1. **时间域 RMS + 自适应噪声底**：`analyser.fftSize=1024`、`smoothingTimeConstant=0.3`，`getFloatTimeDomainData` 填满整个数组算 RMS 能量；噪声底在空闲（未录音/未思考/未播放）时取最小单调逼近，阈值 = `min(0.12, max(0.02, noiseFloor×4))`；
2. **打断阈值**：思考中同阈值（灵敏），TTS 播放中 `max(0.08, noiseFloor×6)`（防回声误判）；
3. **`processVoice` 空转写静默恢复**：`if (!text)` 不再 `throw` 显示「出错」，改为 `setStatus('正在监听...'); return;`；
4. **静音判定 1.5s → 1.2s**，语音到文字更快；
5. **聊天页降级路径同步修复**：`VoiceRecorder.vadLoop` 同样改为 RMS + 自适应噪声底。

**改动文件清单**：`frontend/src/pages/DesktopAssistant.jsx`、`frontend/src/components/VoiceRecorder.jsx`、`项目计划/01_单Agent聊天助手/08_桌面助手详解.md`、`05_前端详解.md`、`04_语音输入与识别详解.md`、`AGENTS.md`。

**验证**：`npm run build` 通过；重建 frontend 容器后浏览器手工清单（正常语速说一句即触发、安静环境不误触发、播放中说话可打断）。

## 五十、桌面助手一句话被切半句 + 语音重叠：静音判定太短 + TTS 播放前未停旧音频

**问题现象**：桌面助手把一句完整的话切半句（前 5s 识别成一句、后 5s 识别成另一句）分别回复；且前/后半句两个回复的语音同时播放重叠；VAD 太灵敏，没等人把话说完（换气/停顿）就开始思考。

**根因分析**（`frontend/src/pages/DesktopAssistant.jsx`）：
1. 静音判定硬编码 `setTimeout(..., 1200)`——人的换气/语速停顿常超 1.2s，长句被切成两句分别触发转写与回复；
2. `finish()` 播放新 TTS 前**未停止旧 audio**：`audioRef.current = audio` 覆盖引用但旧 audio 对象仍在播放，新回复 `play()` 与旧回复重叠出声；后半句说话音量低于打断阈值时不触发 `interrupt()`，两个回复就同时播；
3. VAD 无最小语音时长防护，环境噪声/鼠标声可能误触发。

**解决方案**：
1. **静音判定延长 + 常量化**：`SILENCE_MS=3000`（等约 3 秒换气/停顿再提交转写），`MIN_VOICE_MS=500`（最小有效语音时长，低于此视为噪声误触发丢弃）；
2. **录音开始记录时间戳**：`recorder.start()` 与 `interrupt()` 内 `recStartTimeRef.current = performance.now()`；静音到点先判时长 < 500ms 则丢弃（不转写，静默恢复监听）；
3. **TTS 播放前停旧音频**：`processVoice` 确认有文字后与 `finish()` 播放新 audio 前都 `if (audioRef.current) { audioRef.current.pause(); audioRef.current = null; }`，防两个回复语音重叠。

**改动文件清单**：`frontend/src/pages/DesktopAssistant.jsx`、`项目计划/01_单Agent聊天助手/08_桌面助手详解.md`、`05_前端详解.md`、`AGENTS.md`。

**验证**：`npm run build` 通过；重建 frontend 容器后浏览器手工清单（长句一次转写不切半句、回复播放中说话旧回复立即停、噪声不误触发）。

## 五十三、桌面助手说话后常显示「出错请重试」：KG 检索无兜底 + 前端只显示笼统文案

**问题现象**：桌面助手说完话后经常弹出「出错请重试」，但不知具体是什么环节出错。

**根因分析**：
1. **后端链路存在两处无 try/except 兜底，违反「KG/Chroma 异常降级、绝不阻断聊天主流程」约定**：

3. `DesktopAssistant.jsx`：新增 `friendlyError(raw, code)`（映射 `chat_model_not_configured` / `network_error`，其余直接用后端中文友好句）；`onError` 改为 `(msg, code)` 保存 `{msg, code}`，`finish()` 与 `catch` 均展示具体原因文案，不再只显示「出错请重试」。

**改动文件清单**：`backend/app/core/memory_engine.py`、`frontend/src/pages/DesktopAssistant.jsx`、`项目计划/01_单Agent聊天助手/08_桌面助手详解.md`、`05_前端详解.md`、`AGENTS.md`。

## 五十六、图谱边从未创建成功（rels=0）：Neo4j 5 的 Cypher 属性语法 `element_id` 返回 NULL

**问题现象**：关系网页上自我节点（HHC）已在屏幕中心，但节点之间的边始终不显示；悬停线上也看不到关系名称。此前已在 `Graph3D.jsx` 调深调粗边线并加大 `linkHoverPrecision`（见「五十五」），依然无效。

**根因分析**（后端 `backend/app/db/neo4j_client.py`）：
1. Neo4j 5 的 Cypher 中 `node.element_id`（**属性语法**）返回 `NULL` 并告警 `UnknownPropertyKeyWarning`；正确写法是 `elementId(node)`（**函数语法**）。容器内实测同一节点：`elementId(p)` 返回 `4:7f416bc8-...:5`，`p.element_id` 返回 `None`；
2. 全库所有取 id 的 Cypher（`merge_person`/`merge_thing`/`ensure_self_node`/`get_self_node_id`/`search_persons`/`create_person`/`merge_trait` 等）都写的是 `RETURN p.element_id AS id` → 拿到的 id 恒为 `None`；
3. `memory_engine._persist_reply` 里 `merge_entity` 拿到 None id 后调 `link(None, pred, None)`，`link()` 的 `WHERE a.element_id = $from_id AND b.element_id = $to_id` 恒不匹配 → **边 MERGE 静默不执行**，全库关系数实测为 0（`MATCH ()-[r]->() RETURN count(r)` = 0）；
4. `consolidate_self_refs` 的 `WHERE n.element_id <> $sid` 恒为 null → 「我」节点永不被归并删除，图谱里一直有第二个"自己"；
5. `get_full_graph` 用的是 Python 驱动的 **Node 对象属性** `x.element_id`（返回正确 id），所以节点正常显示，但 links 查询匹配 0 行 → 前端 `links=[]` → 边不渲染、hover 无效。

**解决方案**：
1. `neo4j_client.py` 全部 **Cypher 字符串内** 的 `.element_id` 改为 `elementId(x)` 函数语法（17 处），覆盖：`merge_person`/`merge_thing`/`merge_trait`/`ensure_self_node`/`get_self_node_id`/`resolve_self_ref`/`search_persons`/`create_person`/`add_alias`/`link`/`delete_or_archive`/`consolidate_self_refs`（候选查询、入边/出边转移、删除）/`export_all`/`import_graph`；Python 驱动对象属性 `rec["n"].element_id`（`get_full_graph`、`export_all` 的 nodes 组装）保持原样；
2. **一次性补边脚本**：对所有用户的孤立节点（`NOT (n)--()` 且非自我、非「我/我的/本人/自己/我自己」）执行 `MERGE (self)-[:提到 {user_id}]->(n)`，让历史数据全部连到自我节点；
3. 重建 backend 容器加载新代码。

**改动文件清单**：`backend/app/db/neo4j_client.py`、`AGENTS.md`、`项目计划/01_单Agent聊天助手/03_知识图谱详解.md`。

**验证**：
- 容器内 `grep -c "elementId(" = 21`、`.element_id AS` = 0，确认新代码已部署；
- 容器内链路自测：`merge_person('测试临时实体')` 返回真实 id（不再 None），`link` 后关系数 +1（16→17），`delete_or_archive` 清理成功；
- 补边后全库 `MATCH ()-[r]->()` = 16 条「提到」边（HHC 用户）；`get_full_graph` 返回 17 节点 + 16 links，全部 `source=自我节点 id`、`type=提到`；
- 待浏览器手工清单：关系网页边清晰可见、悬停线显示「关系：提到」、全图经 ≤1 跳连通到 HHC、「我」重复节点消失。

## 五十七、图谱「你」节点突兀 + 实体间无边 + 星空风要求

**问题现象**：修复边不显示（「五十六」）后，图谱出现新的体验问题——节点之间只有「提到」星形边全连到自我节点 HHC，实体之间没有真实关系边；出现突兀的「你」节点；用户希望节点更小、边去掉箭头/流动粒子等动态效果，做成简洁星空感。

**根因分析**：
1. **历史边缺失**：element_id bug 期间历史消息的三元组抽取边（sub→pred→obj）全部没写入，补边脚本只补了 self→实体的「提到」星形边，所以实体间无关系边、图呈放射状；
2. **「你」节点**：抽取模型把对话中的「你」抽成独立实体，而「你/小娜/XIAONA」实际指代聊天机器人本身，应归并到机器人节点而非独立出现；
3. **自环**：回填时三元组 sub/obj 都归并到自我节点会产生 HHC→提到→HHC 自环，3D 图渲染成无意义圆环。

**解决方案**：
1. **前端星空简洁风**（`frontend/src/components/Graph3D.jsx`）：`nodeRelSize=3→1.6`、普通节点 `nodeVal` 系数缩小、自我节点发光球半径 4.2/3.0→2.4/1.7；边去掉 `linkDirectionalParticles/ParticleWidth/ParticleSpeed/ArrowLength/ArrowRelPos/ArrowColor/linkCurvature`，改为静态细线 `linkColor=rgba(99,102,241,0.55)`、`linkWidth=1.5`；保留 `linkLabel` 悬停显示关系名、`linkHoverPrecision=10`；
2. **机器人节点归并**（`backend/app/db/neo4j_client.py`）：新增 `_BOT_REFS`、`ensure_bot_node`（`is_bot=true` 的 Person 节点，名称=小娜）、`get_bot_node_id`、`resolve_bot_ref`；`merge_entity` 在自称归并后追加机器人指代归并；新增 `consolidate_bot_refs` 把历史孤立「你」节点的关系转移后删除；
3. **`link()` 自环防护**：`from_id == to_id` 直接返回不建边（三元组 sub/obj 归并到同一自我节点时的自环无信息量）；
4. **`GET /api/memory/graph` 兜底**（`backend/app/api/memory.py`）：查询前同时执行 `consolidate_self_refs` + `consolidate_bot_refs`；
5. **历史三元组回填**：用提炼模型重跑 HHC 全部 28 条 user 消息的 `extract_triples`，写回实体间关系边（`用户→请求介绍→AI助手`、`小娜→听得到→HHC`、`南山区→位于→深圳` 等），并清理自环边。

**改动文件清单**：`frontend/src/components/Graph3D.jsx`、`backend/app/db/neo4j_client.py`、`backend/app/api/memory.py`、`AGENTS.md`、`项目计划/01_单Agent聊天助手/03_知识图谱详解.md`。

**验证**：
- 回填后图谱 24 节点 29 边（含实体间关系边 6 条 + 「提到」边），「你」节点消失、出现「小娜」（`is_bot=true`）；
- `get_full_graph` 返回的 links 含 `请求介绍/听得到/喜欢/位于/发送方/接收方` 等实体间关系；
- 自环清理后 rel count 29；
- 待浏览器手工清单：节点明显变小、边为简洁静态细线（无箭头/粒子）、悬停线显示关系名、实体间有连线而非纯放射状、「你」节点消失而出现「小娜」。
