## 一、Agent 任务执行通路崩溃：'str' object has no attribute 'get'

### 现象

用户配置执行者/审核者模型后，在聊天页下达数据采集任务（如「找一下北美戒指销量前10的商品」），确认执行后提示：

```
❌ 执行出错：'str' object has no attribute 'get'
```

任务执行通路全线崩溃，数据爬取无法跑通。

### 根因分析

`llm_provider._complete` 带 `tools` 调用（function calling）时，仅在没有 `tool_calls` 时才返回**完整 message dict**；当模型直接给出最终 `content` 字符串（未触发工具调用）时返回的是 **content 字符串**。`executor.py` 对返回值无条件调 `msg.get("tool_calls")` → 字符串没有 `.get` → `AttributeError`。

为什么以前没暴露：此前执行者/审核者模型未配置，任务通路从未真正执行到 executor 的 `chat_with_tools`。

### 解决方案

1. **`backend/app/core/llm_provider.py` `_complete`**：带 `tools` 调用时**始终返回完整 message dict**（含 `tool_calls` 或最终 `content`），由 `chat_with_tools` / executor 消费；普通聊天（`tools=None`）仍返回 content 字符串，不影响现有调用点。
2. **`backend/app/core/agent/executor.py`**：对 `chat_with_tools` 返回值做类型兜底——若底层回归返回字符串，包成 `{"role":"assistant","content": msg}` 再取 `tool_calls`，双保险防崩溃。

### 验证

容器内实测 executor 两条路径（带工具调用 / 直接出最终答案）均不再崩 `'str' object has no attribute 'get'`。

### 改动文件

- `backend/app/core/llm_provider.py`
- `backend/app/core/agent/executor.py`

## 二、Chroma 仍用硬编码 sentence-transformers：配置的 embedding 模型只当「开关」

### 现象

用户质问：在设置页配置了本地 Ollama `bge-m3:latest` 向量化模型，为什么系统还去连 `huggingface.co` 拉 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`？「我配置一个模型，你告诉我它只是个开关，然后实际用另一个模型」。

同时这也是「深度思考中」卡死、语音变慢的元凶：任务请求后一直显示思考中不回复、后端日志反复出现 huggingface.co `MaxRetryError`。

### 根因分析

1. **配置的 embedding 模型从未用于生成向量**：`chroma_client._get_embedder()` 硬编码 `SentenceTransformer(EMBEDDING_MODEL)`（`paraphrase-multilingual-MiniLM-L12-v2`，384 维英文翻译模型）；`memory_engine._model_configs` 解析出的 embedding cfg 只被当布尔开关：`write_chroma=bool(cfgs["embedding"])` / `embedding_enabled=bool(...)`，模型本身从未被调用。
2. **sentence-transformers 初始化联网卡死**：`SentenceTransformer()` 初始化走 `huggingface_hub.model_info` 联网校验模型版本；容器内无法直连 `huggingface.co`（`Network is unreachable`）→ 每次写消息/查记忆都重试 5 次指数退避（约 30s）后才被 try/except 降级吞掉 → 对话/任务全链路卡顿。

### 解决方案

让配置的 embedding 模型真正干活（`backend/app/db/chroma_client.py` 重构）：

1. **`_embeddings(texts, embedding_cfg)` 改走 OpenAI 兼容 `/v1/embeddings`**：`{base_url}/embeddings`（`base_url` 已由 `_ensure_v1` 补齐 `/v1`），body `{"model": cfg["model"], "input": texts}`，带 `Authorization: Bearer`（api_key 非空时），httpx 同步调用、60s 超时（覆盖 bge-m3 冷启动，实测约 5s）。Ollama bge-m3 实测返回 1024 维。
2. **`upsert`/`query` 增加 `embedding_cfg` 参数**：为 None（未配置向量化模型）→ `upsert` 直接 return、`query` 返回空结果，保持「未配置则降级」约定；移除 `_get_embedder()` 与 `sentence_transformers` / `EMBEDDING_MODEL` 依赖。
3. **维度不匹配自动重建**：旧 collection 是 384 维，新模型 1024 维，`upsert`/`query` 捕获维度异常（`InvalidArgumentError: Collection expecting embedding with dimension of 384, got 1024`，按异常名/消息含 `dimension` 判定，避免把网络故障误判为维度问题）后 `delete_collection` 重建再重试一次；SQL 主数据不受影响，向量随后续对话重建。
4. **调用链参数 `bool → cfg` 透传**：`memory_engine.save_chat_message`/`retrieve_memory`/`_persist_user`/`_persist_reply`、`agent/service.py` `_write_session_message`/`_persist_user_and_reply`、`agent/workflow.py` `_write_message`、`feishu.py` `_record_media_meta` 的 `write_chroma`/`embedding_enabled` 参数全部改为 `embedding_cfg`（传 `_model_configs` 的 `embedding` 键，dict 或 None）。
5. **forgetter.py**：摘要向量 `sum_{id}` 的 `chroma.upsert` 按 `msg["user_id"]` 解析各自 `_model_configs(...)["embedding"]` 传入；未配置该用户 embedding 则跳过摘要向量写入（metadata 打标与 KG 蒸馏照常）。
6. **Dockerfile**：移除 `RUN` 中 sentence-transformers 预下载步骤（`config.py` 的 `EMBEDDING_MODEL` 保留仅为兼容，chroma 已不再引用）。

### 验证

- 容器内实测 `_embeddings` 调 `http://host.docker.internal:11434/v1/embeddings` 返回 1024 维；`upsert`+`query` 正常；`embedding_cfg=None` 时 `upsert` 静默跳过、`query` 返回空。
- 维度迁移实测：对现有 384 维 collection 写入 1024 维 → 捕获维度异常 → 重建 → 重试成功，旧向量清空、新向量 1024 维。
- 重建 backend 镜像后：日志**再无 huggingface.co 连接尝试**；`save_chat_message` 走配置的 bge-m3 生成向量并落库成功；`/api/health` 正常。

## 三、聊天页回复变空白小白气泡：打字机收尾不写回 state

### 现象

聊天页下达任务型问题（如「帮我找北美戒指销量前十」）后，先出现「带深度思考框的白色大气泡」，过一会儿气泡消失，变成一个**极小、纯白色、内容全空**的对话气泡，任务确认文案看不到。正常聊天在流式结束时也可能有尾部内容被截断。

### 根因分析

1. **`Chat.jsx` `flushPending()`（打字机收尾）只合并不写回**：流结束时把 `thinkingPendingRef`/`pendingRef` 剩余内容合进**局部变量** `assistantText`/`thinkingText`，但**没有调用 `patchAssistant` 写回 React state**（`patchAssistant` 只在 30ms 定时器 tick 和 `finish` 的 `failed` 分支里调用）。
2. **agent 确认文案是「单帧整段 delta + [DONE]」**：后端 `chat.py` 对 agent 确认回复把整段文案作为**一条** `delta` 帧发出，紧接着 `[DONE]` 同一网络包到达 → `onDelta` 入队后 30ms 定时器**未及 tick** 就触发 `finish` → `flushPending` 后 state 里 `content` 恒为 `''` → `setStreamingId(null)` 后 `ChatMessage` 渲染出一个 content 为空的助手气泡。
3. 正常聊天同样受影响：流式结束时 `pendingRef` 剩余未揭晓的尾部被丢弃（轻微截断）。
4. 对照参考：`DesktopAssistant.jsx` 的 `finish` 正确调用了 `patchTurn({ thinking, content })` 补全最终状态，故桌面助手无此 bug。

### 解决方案

`frontend/src/pages/Chat.jsx` `flushPending()` 末尾补一行：

```javascript
patchAssistant({ content: assistantText, thinking: thinkingText });
```

把合并后的最终内容写回 state。对 `onMediaReply`（先 flushPending 再覆盖 `assistantText=text`）、`onError`/`onDone` 路径幂等，不影响媒体回复气泡与错误提示。

### 验证

- `npm run build` 通过；重建 frontend 容器后 `http://localhost:8080` 引用新产物 `index-Buq2CDuY.js`（含修复代码），HTTP 200。
- 聊天页任务确认文案完整显示并保留，不再塌成空白小白气泡；普通聊天回复尾部不再截断。

### 改动文件

- `frontend/src/pages/Chat.jsx`

### 文档反哺

- `AGENTS.md`：流式打字机约定补充「flushPending 必须把剩余内容 patch 回 state」。本台账即本条。

## 四、聊天页话筒报「不可用」：Web Speech 失败降级路径 AudioContext 无 resume 兜底

### 现象

聊天页（`VoiceRecorder`）点麦克风按钮后显示「语音服务不可用，已自动切换本地识别」，随后红框"录音中"但说话始终不出字、无法语音转文字；**桌面助手实时语音完全正常**。

### 根因分析

1. **Web Speech 主路径在国内网络必然失败**：`VoiceRecorder` 主路径用浏览器原生 Web Speech API（`webkitSpeechRecognition`），识别依赖 Google 服务，网络不可达必触发 `network` 错误 → 弹红色「语音服务不可用」提示（用户看到的"不可用"）→ 降级 MediaRecorder。Chrome 下 `supportsSpeech` 恒为 true，**每次点击都先试 Web Speech、失败、弹提示、再降级**，体验即"话筒坏了"。
2. **降级路径 AudioContext 无用户激活兜底**：`startMediaRecorder()` 里 `new AudioContext()` 后直接 `createAnalyser` 开 VAD，**没有 resume 兜底**。getUserMedia 权限弹窗可能耗尽浏览器 5s「用户激活」窗口，ctx 保持 `suspended` → `AnalyserNode.getFloatTimeDomainData` 全零 → VAD 音量恒 0 → 红框"录音中"但永远检测不到人声。这与桌面助手曾经"监听中但不响应"同根因——桌面助手已修（`DesktopAssistant.jsx` 启动 resume + 一次性手势监听 + VAD 每帧 resume），聊天页漏了。

### 解决方案

`frontend/src/components/VoiceRecorder.jsx`（对齐桌面助手）：

1. **AudioContext 用户激活兜底**：`startMediaRecorder` 建 ctx 后 `suspended` 则 `await resume()`；仍不 `running` 注册一次性 `pointerdown/keydown` 手势监听，用户点击页面时 resume 并自移除（`gestureResumeRef` 记录，`stop()` 与卸载 cleanup 移除防泄漏）；`vadLoop` 的 `tick` 顶部每帧 resume 兜底。
2. **Web Speech 失败记忆 + 静默降级**：`rec.onerror` 的 `network/service-not-allowed/audio-capture` 分支置 `webSpeechFailedRef=true`，仅首次显示温和提示「已自动切换本地识别模式」；`start()` 在 `webSpeechFailedRef` 为 true 时直接走 `startMediaRecorder`——本会话后续点击直达本地识别，不再反复试 Google 服务。

### 验证

- `npm run build` 通过；重建 frontend 容器后 `http://localhost:8080` 引用新产物 `index-qMFL3lJ4.js`（含「已自动切换本地识别模式」文案），HTTP 200。
- 聊天页点话筒不再弹「不可用」，说话实时出字并可发送；桌面助手语音不受影响。

### 改动文件

- `frontend/src/components/VoiceRecorder.jsx`

### 文档反哺

- `AGENTS.md`：聊天页实时语音输入约定补充「降级路径 AudioContext 用户激活兜底 + Web Speech 失败记忆」。

## 五、任务执行过程对用户不可见：新增工具调用/失败回退进度消息流

### 现象

用户反馈：Agent 执行任务（如「找北美戒指销量前十」）时后端在调用工具（function calling），但用户看不到执行到哪一步——调用了什么、是否失败、是否回退重试。用户希望前端能展示「走第几遍通路、用了什么功能、失败回退」的进度。

### 现状

- 后端 `workflow.py` 已在会话写阶段消息：`▶ 开始执行任务` / `🧐 执行完成，正在验收…` / `↻ 审核未通过（第 N 次重做）` / `✅❌ 结果`，但**工具调用细节没有**。
- `executor.py` 调用工具前 `on_log("executor", "call_tool", {tool, args})`，但**工具返回成功/失败没有回调**；`on_log` 是同步回调，无法异步落库写会话消息。
- 前端 `Chat.jsx` 轮询只在 `done/failed/cancelled` 时刷新消息，**执行中不刷新** → 即使有进度消息也不会逐步出现。

### 解决方案（用户确认：消息流展示 + 沿用 3s 轮询，不做 SSE）

1. **`executor.py`**：`on_log` 回调改可 await（两处 `await on_log(...)`）；工具调用后补 `tool_result` 回调 `{tool, ok, error}`，供 workflow 判断失败回退。
2. **`workflow.py`**：新增 `_TOOL_LABELS` 中文映射（`fetch_url`→读取网页内容、`fetch_amazon_bestsellers`→抓取 Amazon 北美商品榜单、`fetch_etsy_trending`→抓取 Etsy 热门商品榜单、`generate_excel`→生成 Excel 表格）+ `_tool_args_summary` 参数摘要；`_on_log` 改 `async def`，拦截两个动作写进度消息：
   - `call_tool` → `🔧 正在{中文标签}{参数摘要}…`
   - `tool_result` 且 `ok=false` → `⚠️ {中文标签}未成功（原因），正在尝试其它方案…`
   - 成功不额外写（最终总结已有结果），避免一进一出刷屏。
3. **`reviewer.py`**：`on_log` 两处调用改 `await`。
4. **`Chat.jsx`**：轮询回调在 `executing/reviewing/revising` 时也刷新当前会话消息（仅当任务 `updated_at` 变化才刷新，避免每 3s 无谓请求；`loadSeqRef` 竞态保护）。

### 验证

- `python -m compileall -q backend/app`、`npm run build` 通过；容器内 `from app.core.agent import workflow, executor, reviewer` 导入正常、`has _TOOL_LABELS=True`。
- 重建 backend + frontend 容器，前端产物含轮询改动（`updated_at` 判断），HTTP 200。
- 聊天页下达任务后对话将逐条出现：`▶ 开始执行任务` → `🔧 正在抓取 Amazon 北美商品榜单（关键词：silver ring）…` →（失败时）`⚠️ …正在尝试其它方案…` → `🧐 正在验收…` →（打回时）`↻ 审核未通过（第 1 次重做）` → `✅ 结果 + 下载链接`。

## 六、数据源工具增强：地区站点 + 价格/评分/评论过滤

### 现象

用户问：「帮我搜一下英国现在卖得最好的戒指前十，他能不能搜得到，还是说只能搜北美？」「价格在 15 美元以上的戒指 top10」「评分 4.5 以上 top10」。此前 `amazon_bestsellers.py` 硬编码 `amazon.com`（北美/USD cookie），无地区参数；返回原始 items，无价格/评分/评论过滤。Etsy 官方 API 无评分字段、无地区概念。

### 根因分析

- Amazon 工具把地区、货币、语言 cookie、链接清洗域名全部写死北美，用户说英国/加拿大/德国时无法命中对应站点；
- 价格/评分/评论门槛只能靠执行者从结果里「自己挑」，工具层没有过滤能力。

### 解决方案（用户确认全部做，纯后端工具增强，不动前端与任务链路）

1. **`amazon_bestsellers.py`**：
   - 模块级 `_SITES` 映射（us/uk/ca/au/de/fr/it/es → {domain, currency, locale}）+ `_SITE_ALIASES` 别名归一（`britain`→uk、`amazon.co.uk`→uk、`germany`→de 等）+ `_normalize_site()`；
   - `_get` 改按站点取 cookie（`i18n-prefs` 用对应货币、`lc-main` 用 `en_US`/`en_GB`/`fr_FR` 等）与 `Accept-Language`；
   - `_clean_product_url` 前缀域名按站点传入（uk→www.amazon.co.uk），`_normalize_items` 透传 domain；
   - 新增 `_parse_price`（支持 `$`/`£`/`€` 前缀、`15,99 €` 欧式逗号、`$15.99 - $25.99` 区间取最低、解析失败返回 None）+ `_reviews_to_number`（`4.5K`→4500、`1,234`→1234、`1.2M`→1200000）；
   - 过滤：`min_price/max_price/min_rating/min_reviews` 在归一后统一过滤，**无法解析的字段不参与过滤**（避免误杀），过滤条件拼进返回 `note`。
2. **`etsy_trending.py`**：`min_price/max_price`（`price.amount` 是「分」，按 `amount/100` 数值比较，不做汇率换算，note 说明按 listing 本币比较）+ `min_favorers`（最低收藏数）。
3. **`executor.py` 系统提示**：新增「地区与筛选」段落——用户指定地区→`site` 参数（未指定默认 us）；价格/评分/评论门槛→`min_price`/`min_rating`/`min_reviews`，不要自己从结果里挑；说明 Etsy 无地区、无评分字段（要评分用 Amazon 源）。
4. **`registry.py`**：两个工具 JSON Schema parameters 补齐新参数描述（单位与默认值）。
5. **`workflow._TOOL_LABELS`**：Amazon 进度消息中文标签由「抓取 Amazon 北美商品榜单」改为「抓取 Amazon 商品榜单」（地区已参数化，不再固定北美）。

### 验证

- `python -m compileall -q backend/app` 通过；

## 七、Amazon 任务“抓取失败”实为条件严苛 + 进度消息一次性输出

### 现象

用户下达任务「查询北美女士钻石戒指销量最好的产品，单价 15 元以上且星级 4.5 以上」，聊天页进度气泡一次性全部出现（不是一条一条出），最后报「❌ 执行达到最大工具调用轮次」。用户质疑：抓取是否真失败？进度为什么一次性输出？

### 根因分析（两个独立问题）

1. **“抓取失败”是假象**：Amazon 抓取实际**成功**（`ok:true`）。日志与 `agent_run_logs` 铁证：执行者传 `min_price=15 + min_rating=4.5`，`women diamond ring` 返回 2 条、`diamond ring` 返回 1 条；不带过滤实测同一关键词返回 20 条，过滤后恰好剩 2 条（$19.99/4.6、$39.99/4.5）——**符合全部条件的商品本就不多**。执行者觉得条数不足「top10」，反复换关键词重试 6 轮全部耗尽，报「达到最大工具调用轮次」。系统提示只教了「失败换词」，没教「条数少是真实结果、应如实交付」。
2. **进度消息一次性输出**：`workflow._on_log` 写进度消息落库时**不更新 `AgentTask.updated_at`**；`Chat.jsx` 轮询**仅当 `t.updated_at` 变化才刷新会话消息**，而任务执行中状态一直 `executing`（updated_at 不动）→ 前端 30s 执行期间一次不刷新，直到 `failed` 才刷新 → 全部进度+失败消息一次性出现。

### 解决方案

1. **`workflow.py`**：
   - `_write_message` 新增 `task_id` 参数，写消息后 `_touch_task` 独立 DB 会话 touch `AgentTask.updated_at`；所有调用点（开始执行 / call_tool 进度 / tool_result 失败进度 / 验收 / 重做 / 最终结果 / 模型不可用）传 `task_id=task_id`——前端轮询据此感知进度变化；
   - `_tool_args_summary` 增强：除 keywords/url/category/filename 外，显示 `site`/`min_price`/`max_price`/`min_rating`/`min_reviews`/`min_favorers`（如 `（关键词：women diamond ring，站点：us，价格≥15，评分≥4.5）`），进度消息体现过滤门槛。
2. **`executor.py` 系统提示**：新增「条数不足不要换词」——工具返回 `ok:true` 且 `items` 非空直接交付（已按用户门槛过滤，条数少如实说明「符合全部条件的商品仅 N 条」），只有 `ok:false` 或 `items` 为空才换词（最多 1-2 次）。
3. **`Chat.jsx`**：Agent 任务轮询间隔 `3000` → `2000`ms（配合后端 touch，进度气泡逐条出现）。
4. **`amazon_bestsellers.py`**：修 `_SearchParser` 链接清洗未传 `domain` 的 bug（非 us 站点商品链接前缀会被清洗成 `www.amazon.com`，`_SearchParser` 构造接收 domain）；过滤后 `len(items) < 3` 时 note 追加「符合全部条件的商品较少，可能受价格/评分门槛限制」。

### 验证

- `python -m compileall -q backend/app`、`npm run build` 通过；
- 本地 + 容器内 mock 全过：`_tool_args_summary` 输出 `（关键词：women diamond ring，站点：us，价格≥15，评分≥4.5）`；`_SearchParser("www.amazon.co.uk")` 解析出 `https://www.amazon.co.uk/dp/...` 前缀链接；过滤回归 + 实证场景（前 20 条过滤后恰为 2 条）断言通过；
- 重建 backend + frontend 容器，前端 HTTP 200、后端 `/api/health` ok；
- 真机复测：进度气泡应逐条出现；严苛条件任务执行者应交付 1-2 条真实结果而非换词耗尽轮次。

## 八、语音输入发送后输入框文字不消失

### 现象

用户语音输入一句话，文字清晰准确地出现在输入框；点发送后聊天框里出现了这条消息，但**输入框里这句话仍在**，需手动删除（重复内容）。

### 根因分析

用户场景实际触发路径：

1. pointerdown（录音中点击发送按钮）→ `VoiceRecorder.stop()` 自动停止 → `recognition.stop()` 是**异步**的，React flush 后 `listening` 已变 `false`；
2. click → `ChatInput.handleSend`：此时 `listening` 已是 `false` → **跳过 `stopAndGetText` 分支** → `content = text.trim()` 直接读 state → `onSend` 发送 → `setText('')` 清空输入框；
3. 稍后 `recognition.onend` 才到达（`stop()` 异步，onend 延迟几十~几百 ms）→ `flushTextAndResolve()` → **`emitText()` 无条件把 `finalRef.current` 缓存的语音文字 `onInterim` 写回输入框** → 文字"复活"。

降级路径（MediaRecorder）同理：`onstop` 转写完成的 `flushTextAndResolve` 延迟 `emitText` 写回。

### 解决方案

1. **`VoiceRecorder.jsx`**：新增 `sentRef`（本次语音文本已发送标志）+ `markTextSent()`；`emitText` 开头拦截 `if (sentRef.current) return;`——已发送后不再刷新输入框，阻断 `onend`/`onstop` 延迟写回；`start()` 重置 `sentRef.current = false`（新一轮语音输入重新允许刷新输入框）；`useImperativeHandle` 暴露 `markTextSent`。
2. **`ChatInput.jsx`**：`handleSend` 在 `await onSend(...)` + `setText('')` + `setFiles([])` 后调用 `voiceRecorderRef.current?.markTextSent?.()`。

时序验证：
- 语音输入完成点发送（listening=false）：`setText('')` 清空 → `markTextSent()` → onend 延迟 `emitText` 被 `sentRef` 阻断 → 输入框保持空；
- 录音中点发送（listening=true）：走 `stopAndGetText` await，onend resolve + emitText 写满 → 发送 → `setText('')` → `markTextSent()` → 无后续写回；
- 打字发送：`markTextSent` 仅设标志，VoiceRecorder 无 `emitText` 触发，无影响；下次语音 `start()` 重置。

### 验证

- `npm run build` 通过；重建 frontend 容器，前端 HTTP 200、后端 `/api/health` ok；
- 手动复测：语音输入一句话 → 点发送 → 聊天框出现消息且输入框清空；再语音输入新话 → 输入框正常实时显示；打字发送不受影响。
