## 一、清空数据外键 500：只删 messages→sessions 触发 IntegrityError

### 现象

设置页「清空数据」在跑过 Agent 任务或绑过飞书的账号上执行失败：`agent_tasks.session_id`、`feishu_session_map.session_id` 引用 `sessions.id` 且无 `ON DELETE CASCADE`，删 sessions 时 `IntegrityError`，同事务回滚，清空实际不可用。

### 根因分析

`sql.clear_messages_and_sessions` 只删 messages→sessions，未处理 `agent_tasks` / `feishu_session_map` 对 `sessions.id` 的外键依赖。

### 解决方案

`backend/app/core/memory_engine.py` `clear_messages_and_sessions` 按外键依赖逆序删除：
`AgentRunLog(task_id→agent_tasks)` → `AgentTask(session_id→sessions)` → `FeishuSessionMap(session_id→sessions)` → `Message` → `Session`（均带 `user_id` 过滤 + `synchronize_session=False`）。`FeishuSessionMap` 无 `user_id` 列，按「先取该用户全部会话 id，再按 session_id 过滤」删除。

### 验证

容器内构造 AgentTask + AgentRunLog + FeishuSessionMap + Message + Session 依赖链后执行清空：全部 0 残留、无异常。

### 改动文件

- `backend/app/core/memory_engine.py`

### 文档反哺

- `AGENTS.md`：会话软删除约定补充「清空数据按 FK 依赖逆序删除」。

## 十、验证中实测抓出的新 Bug：get_recent_messages 在 limit 之后 filter

### 现象

实现 `exclude_ids` 后，实测 `retrieve_memory(exclude_ids=[mid])` 抛 `sqlalchemy.exc.InvalidRequestError: Query.filter() being called on a Query which already has LIMIT or OFFSET applied. Call filter() before limit() or offset() are applied.`

### 根因分析

`get_recent_messages` 先把 `.limit(k*2)` 接在 query 链上，再在 `exclude_ids` 非空时追加 `.filter()`——SQLAlchemy 不允许 LIMIT 之后再加过滤条件。

### 解决方案

把 `filter` 移到 `limit` 之前：query 先构造「过滤 + 排序」，`exclude_ids` 过滤后最后 `.limit(k*2)`。

### 验证

修复后 `retrieve_memory(exclude_ids=[mid])` 正常返回，recent 不含当前消息。

### 改动文件

- `backend/app/core/memory_engine.py`

### 严重 1：fetch_session_messages 升序取旧消息（核心功能失效）

**现象**：`fetch_session_messages.py` 用 `order_by(Message.created_at.asc()).limit(limit)`——取到会话**最早** N 条，与 docstring/registry/executor 提示/04/05 文档声称的「最近 N 条」相反。长会话下「把刚才的对话整理成文档」整理的是开头寒暄。

**根因分析**：查询方向错误，`asc()` 应取 `desc()`。

**解决方案**：`order_by(Message.created_at.desc())` + `.limit(limit)` + `list(reversed(rows))` 保持时间正序返回。

**改动文件**：`backend/app/core/agent/tools/fetch_session_messages.py`

**待手动验证**：会话写入 >limit 条消息后触发整理文档，产物应为最近 N 条而非开头。

### 中 2：generate_pdf 图片强制拉伸成正方形

**现象**：`Image(path, width=min(90*mm,300), height=min(90*mm,300))` 双维度独立缩放，非方图变形。

**解决方案**：只传 `width=min(90*mm, 300)`，高度由 reportlab 按原始宽高比自动计算。

**改动文件**：`backend/app/core/agent/tools/generate_pdf.py`

**待手动验证**：嵌入非方图生成 PDF，图片不变形。

### 中 3：generate_pdf 表格列宽基准 540 超 A4 可用宽度

**现象**：A4 页宽 595pt − 左右边距各 40pt = 可用 515pt；基准 `540 // len`，5 列 → 108×5=540 > 515，reportlab `Table` 超宽抛 `LayoutError`（榜单表恰是 5 列）。

**解决方案**：基准改 `515`（可用宽），表达式 `max(40, min(120, 515 // max(1, len(headers))))`。

**改动文件**：`backend/app/core/agent/tools/generate_pdf.py`

**待手动验证**：5 列榜单表生成 PDF 不报 LayoutError。

### 中 4：fetch_url SSRF 不覆盖重定向

**现象**：`follow_redirects=True` 静默跟随，`_ssrf_check` 只校验初始 URL——公网 302 到 `169.254.169.254` / `chroma:8000` 等内网即可绕过。

**解决方案**：`follow_redirects=False`，手动循环处理 3xx（最多 5 跳），每跳解析 + `_ssrf_check`，超跳数返回结构化错误。

**改动文件**：`backend/app/core/agent/tools/fetch_url.py`

**待手动验证**：302→内网地址返回「该地址不允许抓取」拦截错误。

### 中 5：fetch_session_messages 混入任务进度消息

## 十四、语音输入追加模式 + 发送后输入框残留修复

### 现象

1. 语音输入发送后输入框文字不消失（「发送了但文字还在」）；用户希望：点发送后**不管手动输入还是语音转写**，输入框全部清空。
2. 用户希望点麦克风转写是**追加模式**：不清掉输入框已有内容，可多次录音无限累加（如先手打一段、再录音追加）；只有点一次发送才全清。

### 根因分析

- 残留根因：`VoiceRecorder.jsx` 主路径（Web Speech）`rec.onresult` 直接调 `onInterim`，**绕过** 8-23 加的 `sentRef` 拦截（`markTextSent` 只拦了 `emitText` 路径）。发送后 `setText('')` 已清空，但迟到的 `rec.onresult`（final 落定）又把文字写回输入框。
- 追加模式缺失：`ChatInput.jsx` 的 `onInterim={(t) => setText(t)}` 是**整体替换**——录音一开头就把输入框已有内容覆盖成语音文本，不是追加。

### 解决方案

1. `VoiceRecorder.jsx` `rec.onresult` 开头加 `if (sentRef.current) return;`（迟到的识别结果不再写回）。
2. `ChatInput.jsx` 追加模式：
   - 新增 `voiceBaseRef`，`onRecordingChange(v)` 且 `v=true`（录音开始）时 `voiceBaseRef.current = text`（记录当前输入框已有内容作基准）；
   - `onInterim={(t) => setText(voiceBaseRef.current + t)}`（语音转写追加到已有内容后）；
   - `handleSend` 录音中发送时完整内容 = `voiceBaseRef.current + voiceText`（不能用 `text` state——`await stopAndGetText` 期间 React setState 未提交，读到旧值）；
   - 发送后 `setText('')` + `markTextSent()` 保持全清。
3. 多轮录音：停止后输入框已是「已有 + 上轮语音」，再次录音 `voiceBaseRef` 以该值为基准继续累加。

### 改动文件

- `frontend/src/components/VoiceRecorder.jsx`
- `frontend/src/components/ChatInput.jsx`

- 实测点：手打一段 + 录音追加；多轮录音累加；发送后输入框彻底清空；录音中点发送 = 一次完成「关麦 + 发送 + 全清」。

## 二十、榜单表格 markdown_table 生成 AttributeError

### 现象

用户实测「北美 top10 成人女性钻石戒指」任务：进度消息反复报「⚠️ 抓取 Amazon 商品榜单未成功（工具执行异常：AttributeError）」，换关键词重试 4 次全挂，最后「❌ 执行达到最大工具调用轮次，任务未能完成」。

### 根因分析

上一轮「十九」新增的后端表格生成 `_cell()` 有低级 bug：

```python
def _cell(text: str) -> str:
    t = (text or "").strip()   # rank 是 int：1 or "" → 1 → 1.strip() 抛 AttributeError
```

- `amazon_bestsellers.py` `_build_markdown_table` 里 `_cell(it.get("rank"))`，`rank` 是 int（`it["rank"] = i`）；
- `etsy_trending.py` 同样 `_cell(it.get("rank"))` 与 `_cell(it.get("num_favorers"))`（int）。

触发链路：工具抓取成功 → 组装返回 `markdown_table = _build_markdown_table(items)` → `_cell(int)` 抛 `'int' object has no attribute 'strip'` → 整个工具异常 → executor 报「工具执行异常：AttributeError」→ 换词重试继续炸 → 耗完轮次。

### 解决方案

两个文件的 `_cell` 统一改为：先判 `None` 填「-」，再 `str(text).strip()` 兼容 int/float（数字 `0` 保留不被 falsy 吞掉）：

```python
def _cell(text) -> str:
    if text is None:
        return "-"
    t = str(text).strip()
    if not t:
        return "-"
    t = t.replace("|", "｜").replace("\n", " ").replace("\r", " ").replace("\t", " ")
    t = re.sub(r"\s+", " ", t)
    return t or "-"
```

## 二十三、Google Trends 数据源接入与 TikTok 调研

### 背景

用户对单平台数据不满足，希望多平台交叉验证里能判断「品类是否上行」（如"当下卖得好≠趋势上行"），并问了小红书/抖音（TikTok）/淘宝/京东等平台可不可拿数据。经调研给出结论：**国内平台（小红书/淘宝/京东/抖音）全部需登录/反爬严重/数据非公开，均不可行**；海外可免注册拿数据的仍是以往那几类，其中 **Google Trends** 可做趋势维度、**TikTok Creative Center** 浏览器免登录可看但自动化不可行。用户决定：**接入 Google Trends（零依赖方案），TikTok 暂缓**。

### 根因/调研结论

1. **原版 pytrends 已死**：官方仓库 2025-04 归档停维护，官方 Trends API 仍 alpha 白名单申请不到——最优解是**零依赖 httpx 直连匿名内部接口**（复现 pytrends 底层原理），免注册免 key 不新增依赖。
2. **TikTok Creative Center 自动化不可行**：浏览器免登录可看 Top Products（销量区间+销售增长、按区域/品类/7 天/30 天筛选），但内部 `creative_radar_api` 需签名头 + 住宅代理 + 无浏览器环境（无法执行 JS 签名），批量自动化不可行；按用户决定暂缓，仅把结论记入文档（半自动手动粘贴为可选方向）。
3. **国内平台（小红书/抖音/淘宝/京东）**：数据需登录/私域接口/反爬严重/销量不可见，均不接入。

### 解决方案

- **新建 `backend/app/core/agent/tools/google_trends.py`**：`fetch_google_trends(params, ctx)` → `{ok, source:"google_trends", keyword, geo, timeframe, interest_over_time, trend, by_region, summary, note?}`。
  - 零依赖 httpx 复现 pytrends 原理：首次 `GET /trends/api/explore`（UA + 响应 `)]}'\n` strip + NID cookie），按 title 定位「Interest over time」→ `/api/widgetdata/multiline` 拿时间序列、「Interest by region」→ `/api/widgetdata/comparedgeo` 拿地区分布；`httpx.AsyncClient(timeout=15, follow_redirects=True, trust_env=True)` 自动读容器 `HTTP(S)_PROXY`（国内环境经 Clash 代理）。
  - 参数：`keyword`（必填，品类英文关键词）、`geo`（默认 `US`，可传 `US-CA`/`GB` 或空=全球）、`timeframe`（默认 `today 3-m`，支持 `today 7-d`/`1-m`/`3-m`/`12-m`，非法值回退默认）。
  - 派生指标：`trend` 用时间序列首 1/4 段均值 vs 尾 1/4 段均值，涨幅 >10% 判「上升」、跌幅 >10% 判「下降」、否则「平稳」；`summary` 一句话（热度峰值/走势/热度最高地区）。
  - 降级：超时/连接失败/被墙/解析失败一律返回结构化 `{ok:false, error}`，**不阻断**主流程（符合三模型弹性/数据源降级约定）。
- **`registry.py` 注册**：`_make_tools()` 加 spec（`keyword` 必填 + `geo`/`timeframe`），`handlers` 加 `"fetch_google_trends": fetch_google_trends`。

## 二十六、任务执行韧性修复：模型超时不丢数据 + Trends 429 退避

### 背景

2026-08-27 用户实测「北美前 10 销量最好的成人女性钻石戒指」任务：Google Trends 连续两次 HTTP 429（`diamond ring`、`diamond ring women`），随后任务直接「❌ 执行出错：模型响应超时，请稍后重试」——明明 Amazon 榜单数据已抓到，最终却什么都没有。

### 根因分析

1. **模型响应超时（致命）**：执行者第 3 轮 `llm.chat_with_tools`（非流式）超时。全局 httpx client 超时 120s，大上下文 + DeepSeek reasoning 时偏紧。`TimeoutError` 从 `executor.run` 直接穿透，`workflow.start_task_async` 的兜底捕获后用 `{"success": False, "summary": ..., "artifacts": [], "log": []}` 重建 result——**`tool_results` 为空**，`_format_ranking_table` 拿不到已抓取的 Amazon 榜单表格，数据全丢，任务整体失败。
2. **Google Trends HTTP 429**：Google 匿名接口按 IP 短时限流（请求经 Clash 代理出口）。工具对 429 无特殊处理（不重试不退避）；提示词虽写「勿因失败重试」，LLM 仍换关键词补调一次 Trends，浪费一轮且仍 429。
3. **查询词冗余（次要）**：执行者同时传 `keywords:"diamond ring"` 与 `category:"diamond ring women"`，`amazon_bestsellers.py` 的 `parts = [keywords, category, keyword, color, material]` 直接 `" ".join` 拼成 `diamond ring diamond ring women`，搜索结果失真混入耳环/派对杂物，逼 LLM 多跑一轮带排除词的重抓。

### 解决方案

- **`llm_provider.py` per-call timeout**：`_complete` 增加 `timeout: float | None = None` 参数，`self.client.post(url, ..., timeout=timeout)`（None 沿用 client 默认 120s，不破坏现有调用）；`chat_with_tools` 透传。
- **`executor.py` 单轮超时重试 + 失败保留数据**：每轮 `llm.chat_with_tools(..., timeout=300)`（大上下文 + reasoning 放宽）；包 try/except（`TimeoutError`/`ConnectionError`）首次超时重试 1 次，重试仍失败不抛异常，返回 `{success: False, summary: "模型响应超时，但已抓取到部分数据（见下方榜单表格），可重试获取完整总结。", artifacts, tool_results, log}`——**保留已收集的 `tool_results`**，workflow 的 `_format_ranking_table` 把已抓到的榜单表格附加到失败消息，用户不空手而归。提示词强化：同一数据源失败（含 Trends 429/超时）**最多重试 1 次**，重试仍失败立即放弃该源。
- **`google_trends.py` 429 退避重试**：explore 返回 429 时 `asyncio.sleep(3)` 重试 1 次；仍 429 返回 `{ok:false, error:"Google Trends 临时限流（HTTP 429），已自动重试仍失败，跳过该信号"}`（不阻断基线其它源）。
- **`amazon_bestsellers.py` 查询词去重**：组装搜索词前丢弃被其它更长 part 包含的词（子串匹配），避免 `diamond ring diamond ring women` 类重复词查询。
- **`workflow.py` reviewer 异常降级**：`reviewer_review` 调用包 try/except，异常时降级 `{passed: True, issues: []}`，防审核模型超时把任务永远卡在 `reviewing`。

## 二十七、Google Trends 限流根治：会话保持 + 缓存节流 + 长退避熔断

### 背景

二十六修复后用户实测仍持续报「Google Trends explore 请求失败（HTTP 429）」。用户明确要求**真正解决限流本身**（还想继续用这个信号源），而非绕开或砍掉。

### 根因分析

429 的核心不是重试次数不够，而是**每次调用都新建无 cookie 的 httpx 会话**：
1. 原实现每次 `async with httpx.AsyncClient(...)`，全新会话、不带 cookie——Google 对「无 cookie 新访客」的连续请求极其敏感，短时间几次就 429。
2. LLM 失败后换关键词重试，同一出口 IP 短时间内连打 explore，限流加剧。
3. 26 修复的 3s 退避对 IP 级限流无效（限流窗口分钟级起），429 后立刻重试必再 429，且越打越重。

### 解决方案（三件套）

- **模块级 Cookies 会话保持**：`_JAR = httpx.Cookies()`，`AsyncClient` 传 `cookies=_JAR`。首次 explore 响应的 `set-cookie: NID` 自动存入 jar 复用——Google 对「带 cookie 老访客」与「裸奔新 bot」限流阈值显著不同。**坑（2026-08-27 实测）**：初版误写 `httpx.CookieJar()`（那是标准库 `http.cookiejar`/`requests` 的 API，httpx 0.28.1 无此类）→ 模块级 import 时 `AttributeError: module 'httpx' has no attribute 'CookieJar'`，后端 uvicorn 启动即崩；`compileall` 只查语法不执行模块级语句所以静态检查通过、运行时才暴露。已改为 `httpx.Cookies()`。教训：httpx 的 cookie jar 类是 `Cookies`，勿混用 requests 风格 API。
- **结果缓存 + 全局节流**：模块级 `_CACHE`，key=`f"{keyword}|{geo}|{timeframe}"`，TTL 6h；命中深拷贝返回零请求（任务内换词重试/跨任务同品类不重复打）。模块级 `_last_req_at`，距上次请求 <5s 则 sleep 补齐。
- **429 长退避 + 熔断**：429 时 sleep 30s 重试 1 次；仍 429 置 `_circuit_until = now + 900`（15 分钟熔断），期间直接降级返回「Google Trends 临时限流（HTTP 429），已进入短时冷却，跳过该信号」，不再打 Google。
- **佐证源失败静默（workflow）**：`_SILENT_DEGRADE_TOOLS = {"fetch_google_trends", "fetch_pinterest_trends"}`——这两个纯佐证信号源失败不写 ⚠️ 进度气泡，任务照常交付（此前每次 429 都弹红条吓用户）。
- **提示词改「尽力而为信号源」（executor）**：Google Trends 从「基线三源必须并行调用」降为「尽力而为的信号源：调用 1 次失败即跳过、勿换关键词重试（工具内部已自动重试+冷却），不影响 Amazon/Movers 交付」；最终总结「品类搜索热度处于…期」改为**有则补**，Trends 不可用时不提或标「品类热度信号暂缺」。

## 二十八、榜单任务修复：表格保留严格结果 + Movers 重试 + Trends 拦截识别

1. **表格展示错位（最关键）**：任务里 `fetch_amazon_bestsellers` 被调了两次——第 1 次 `diamond ring + Jewelry` 排除词不全（`toy,party,kids,children,men,mens`，**无 earring/stud/nose/piercing**）→ 结果混入 PAVOI 耳环、Volance 玩具戒指、鼻环；第 2 次 `diamond ring women` 排除词加全 → 严格筛选后只剩 1 条真戒指（IMOLOVE）。但 `workflow._format_ranking_table` 同源去重**保留第一次**结果 → 表格展示「宽松第 1 次」的 7 条耳环玩具表，与总结错位。
2. **Movers 反爬**：`gp/movers-and-shakers` 页面比搜索页对匿名访问更严，`amazon_bestsellers._get` 非 200 直接抛 `RuntimeError` 且无重试（bestsellers 主路径走 `/s?k=` 搜索页所以成功）。
3. **Trends 解析失败**：限流根治后不再 429，但 explore 返回 200 且 body 是 HTML 验证页（非 `)]}'` JSON 前缀），`json.loads` 抛 JSONDecodeError，无重试。
4. **category 大类目词**：执行者传 `category: Jewelry` 并入搜索词 → `diamond ring Jewelry` 放大无关商品池，耳环鼻环全进来，逼出第二次严格筛选。

### 解决方案

- **`workflow._format_ranking_table` 同源保留最后一次**：正序遍历收集 `first_order` + `latest[name]=table`（后出现覆盖），按 `first_order` 顺序拼输出——执行者最后一次调用通常排除词更全、筛选更严，表格与总结不再错位。
- **`amazon_bestsellers._get` 非 200 加重试**：非 200 时 sleep 2s 重试 1 次（Movers/bestsellers 共用），仍非 200 才抛 `RuntimeError`；补 `import asyncio`。
- **`google_trends` 拦截页识别 + 解析失败重试**：explore 响应非 `)]}'` 前缀（200 但 HTML 验证页/拦截页）→ 记日志后 sleep 30s 重试 1 次，仍异常返回「Google Trends 返回人机验证/拦截页，已自动重试仍失败，跳过该信号」；`json.JSONDecodeError` 同样重试 1 次；429 仍走熔断分支。
- **`executor` 提示词禁大类目词**：「关键词要贴合具体品类」句补「**category 只传具体品类词（如 ring/watch），禁止传 Jewelry/Accessories 等大类目词**——大类目并入搜索词会放大混入耳环/玩具等无关商品」。

## 二十九、Amazon Movers 稳定性增强：完整指纹头 + 类目子页优先 + 静默降级

### 背景

二十八轮修复后，Movers（`fetch_amazon_movers`）仍连续 2 次非 200 失败，而 Best Sellers 主榜成功。用户疑问：「不是说免费的公开 API 吗，怎么跑不通」。

### 根因分析

1. **Movers 不是 API，是网页爬取**：Amazon 官方数据接口是 SP-API（需卖家账号 + 收费），我们从未接入。Best Sellers（搜索页 `/s?k=`）与 Movers（`/gp/movers-and-shakers`）都是**公开网页爬取**——免 key 但受 Amazon 反爬控制。
2. **`/gp/` 路径反爬更严**：`gp/` 前缀页面是内部/联盟系统路径，Amazon 对匿名 bot 重点拦截；且容器请求是数据中心 IP、无 cookie、无 JS 环境，特征就是典型 bot。
3. **请求头太裸**：`_site_headers` 只有 `User-Agent` + `Accept-Language` 两个字段，缺少 Accept/Encoding/Sec-Ch-Ua 等浏览器指纹头。
4. **失败弹 ⚠️ 吓用户**：Movers 不在 `_SILENT_DEGRADE_TOOLS`，失败会写「⚠️ 抓取 Amazon 24 小时涨幅榜未成功…」进度气泡，观感是「又报错」。
5. **无类目子页维度**：Movers 全站页反爬最严，类目子页（`/gp/movers-and-shakers/{slug}`）有时更宽松，且用户场景（如钻石戒指）其实更关心 Jewelry 类目涨幅。

### 解决方案

- **`amazon_bestsellers._site_headers` 升级完整浏览器指纹头**：补 `Accept`（text/html 全链 + 图片类型）、`Accept-Encoding: gzip, deflate`、`Cache-Control: max-age=0`、`Connection: keep-alive`、`Upgrade-Insecure-Requests: 1`、`Sec-Ch-Ua`/`Sec-Ch-Ua-Mobile`/`Sec-Ch-Ua-Platform` 三件套——bestsellers/movers 共用经 `_get` 调用，一并受益。
- **`amazon_movers` 类目子页优先 + 回落全站页**：新增 `_MOVERS_CATEGORY_SLUGS` 映射（jewelry/watches/beauty/electronics/toys-and-games/sports-and-outdoors/home-and-kitchen 等，**2026-08-27 WebFetch 逐一验证 jewelry/watches/toys-and-games/beauty/electronics slug 有效**，slug 命名 = 类目名小写连字符）+ `_normalize_movers_category`（英文直查 + 中文经 `_translate_zh_keywords` 翻译后命中）。`fetch_amazon_movers` 新增 `category` 参数：显式 `url` 优先；否则命中 slug 表抓类目页，类目页无数据/失败（`_get` 异常/`_is_bot_check`/解析空）**自动回落全站页**再抓一次保住「起量预警」信号，降级原因记入 `note`。返回契约不变。
- **`workflow._SILENT_DEGRADE_TOOLS` 加 `fetch_amazon_movers`**：Movers 失败静默不弹 ⚠️ 气泡（起量预警维度缺失不影响 Amazon 主榜交付）；Movers 仍是 `_RANKING_TOOLS`，成功时表格照常自动附加。
- **`executor` 提示词同步**：Movers 段补 `category` 用法（命中内置类目表抓该类目涨幅榜、未收录回落全站）+ 「失败静默跳过勿反复重试，最终总结按可用源标『起量预警：…』或『起量预警暂缺』」。
- **`registry.py` Movers schema**：补 `category` 参数描述，`url` 描述类目页示例改为 slug（`.../movers-and-shakers/jewelry`）。

## 三十、榜单候选池扩充（翻 5 页）+ Trends/Movers 改为可选

### 背景

用户实测两个问题：
1. **要 top10 只返回 1 条**：「给我北美 top10 成人女性钻石戒指，不要玩具/派对/耳环/项链」→ 表格只有 1 条真戒指。用户一针见血：「你要 top10，是不是至少要拿到前一百，比较筛选完再留 top10？你先拿 10 个再筛，筛完肯定不够 10 个了」。
2. **Trends/Movers 测试基本失败**：用户连续测试 Google Trends / Amazon Movers 均失败，质疑「默认降级的意义是啥？没有这功能删了不更简单？我的目的是让他成功」。

### 根因分析

1. **候选池太小**：`fetch_amazon_bestsellers` 搜索路径只抓**第一页**（约 16~20 个商品），排除 玩具/派对/耳环/项链 后真戒指就剩 1~3 条。过滤顺序虽已「先过滤后取足条数」（2026-08-24），但**源头候选池本身不足**——用户「先拿前一百再筛」的直觉完全正确。搜索页翻页参数是 `&page=N`，代码根本没翻页。
2. **Trends/Movers 成功率受出口 IP 质量决定**：容器数据中心 IP（Clash 节点）被 Google/Amazon 标记后，重试/指纹头只能提高成功率，不能保证成功。「默认必调」只会让每次任务白白等待 + 占用轮次。

### 解决方案

- **`amazon_bestsellers` 搜索路径翻 5 页**：新增 `_MAX_SEARCH_PAGES = 5` / `_PAGE_DELAY = 1.2`，搜索 URL 加 `&page=N`（1~5，约 80~100 候选）；逐页解析后按 `product_url`（ASIN）去重合并；页间 `await asyncio.sleep(1.2)` 节流；单页失败/被拦用已抓到的页继续、候选池为空才报错。BSR 类目页路径保持单页（非主诉求）。
- **executor 交叉验证提示词重构**：默认第一步**只调 `fetch_amazon_bestsellers`**（现状主榜）；`fetch_amazon_movers`/`fetch_google_trends` 改为**可选**——仅当用户明确提到「起量/涨幅/趋势/热度/会不会火/正在上升」等维度才调用，默认不调；Etsy/Pinterest 维持可选叠加层；最终总结「只补实际调用且成功的源」。条数不足段更新为「翻页抓取约 100 候选、先排除后取足 top N」。

## 三十一、数据源边界如实告知：超纲请求不硬凑

### 背景

用户实测后进一步要求：当请求超出当前数据源能力范围时（如「前 10 个下降最快的商品」——商品级下降榜无公开数据源），执行者要诚实告知「没有这个公开数据源」，而不是硬凑、静默失败或拿别的维度冒充；有数据源的就照常给。

### 根因分析

执行者提示词此前只有「失败/条数不足如实说明」两层兜底，**没有「维度超纲如实告知」这一层**——用户要的商品级下降榜这类无源维度，执行者可能硬凑、用别的维度冒充，或静默不交付。

### 解决方案

executor 提示词「地区与筛选」段后新增「**数据源边界如实告知（2026-08-27 起）**」段：

- **可提供维度清单**：现状销量榜（Amazon Best Sellers，翻 5 页约 100 候选）；24h 上升/起量榜（Amazon Movers，**仅「上升/在涨」方向**，无下跌榜）；品类热度走势（Google Trends，可判 上升/下降/平稳，**关键词级非商品级**）；Etsy 热门榜（需 key）；Pinterest 趋势词（需 token）。
- **无源维度清单（用户问到必须如实说明，勿硬凑/勿伪造/勿用其它维度冒充）**：
  - 商品级「下降最快/跌幅最大」榜单——只有品类热度下降（fetch_google_trends），没有具体商品的下跌榜；
  - 单品总销量/累计销量绝对值——各平台均不公开，只有排名/评分/评论数等相对指标；
  - 国内平台（小红书/抖音/淘宝/京东）数据——尚未接入。
- **处理规则**：请求维度不在能力范围 → 直接告知「当前没有公开数据源可抓取该维度」，有最接近的可替代维度则说明并提供（如「商品级下跌榜没有，但我可以给你品类热度是否在下降、以及当前卖得好的 top N」）；已有维度照常交付，不因缺某个维度而放弃整个任务。
