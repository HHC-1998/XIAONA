## 一、全量审核后端修复（6 项：1 高危 + 2 中危 + 3 中低）

### 背景

用户要求对「榜单/选品任务」前后端功能做一次完整审核（覆盖候选池扩充、Movers 稳定性、Trends 限流、表格展示、数据源边界告知等多轮改动）。三个并行审计代理分别核查了：后端 Agent 数据链路（工具→workflow→消息）、前端展示链路（SSE→轮询→表格/下载）、API 与消息持久化层。结论：**前后端契约整体咬合，无阻断 bug**，但发现 6 项后端问题需修复。

### 一、高危：确认词把「拒绝」误判成「执行」（director.py）

**问题现象**：用户在确认反问阶段回复「不行/不可以/不好」，后台仍启动任务执行（烧 token）。

**根因分析**：`classify_confirmation` 的 `_STRONG_CONFIRM` 含单字「行/好/可以/同意」等，且强肯定判定在强否定之前——「不行」含「行」、「不可以」含「可以」、「不好」含「好」全部命中强肯定，被判为 `yes`。AGENTS.md 此前只防了「没问题」被「没」误杀（2026-08-19 台账二·Bug1），没防「不X」被确认词误杀。

**解决方案**：强肯定判定**之前**新增「不+确认词」否定组合预检——`if any(f"不{n}" in compact for n in ("行", "可以", "好", "确认", "执行", "同意", "开始")): return "no"`。输入去空白归一化（`compact = re.sub(r"\s+", "", r)`）兼容「不 行」等带空格输入。其余判定顺序（强肯定→强否定→弱否定→弱肯定→LLM）保持不变，「没问题」仍由强肯定先拦截。实现上用 `compact` 只做预检、主判定仍用原始 `r`（避免去掉全角/英文多词空格造成回归）。

**改动文件**：`backend/app/core/agent/director.py`

### 二、中危：听不清（other）时对话不落库（service.py）

**问题现象**：pending 确认阶段用户回复无法判定（如没听清重问、答非所问），`classify_confirmation` 返回 `other`。刷新会话后，用户这句话与机器人重问消息**消失**。

**根因分析**：`handle` 的 other 分支直接 `return HandleResult(reply=...)`，未调 `_persist_user_and_reply`；而 no/yes 分支都落库。SSE 当时显示了，但刷新后历史缺这两条。

**解决方案**：仿照 no 分支补 `_persist_user_and_reply`（写 pending 会话 + embedding 配置）。

**改动文件**：`backend/app/core/agent/service.py`

### 三、中危：category 大类目词矛盾（amazon_bestsellers.py + registry.py）

**问题现象**：executor 提示词声明「category 禁止传 Jewelry/Accessories 等大类目词」（2026-08-27 起），但工具代码**零拦截**，且 registry schema 与工具 docstring 还把 Jewelry 列为合法示例——LLM 按示例传「Jewelry」完全合法，大类目词混入搜索词放大混入耳环/玩具，逼出第二次严格筛选。

**根因分析**：口径不一致——提示词约束了，但工具端没有兜底，schema 还给出了相反示例。

**解决方案**：
- `amazon_bestsellers.py` 新增模块级 `_BROAD_CATEGORY_WORDS` 集合，组装 `parts` 时**整词命中**大类目词的参数剔除（不拆散 `jewelry box` 等多词合法品类），记入 note「已忽略大类目词 …（改用细分品类词更准）」；只剩大类目词时兜底保留一个避免直接报错。
- `registry.py` 的 `fetch_amazon_bestsellers` description 与 `category` 参数描述移除 `Jewelry` 示例，标注「禁止传 Jewelry/Accessories 等大类目词，工具会整词剔除」；docstring 同步。

**改动文件**：`backend/app/core/agent/tools/amazon_bestsellers.py`、`backend/app/core/agent/tools/registry.py`

### 四、中低：Google Trends 前导空白误判（google_trends.py）

**问题现象**：响应带前导空白/换行时，拦截检测（`resp.text.lstrip().startswith(")]}'")`）通过但 `_strip_prefix` 只认 `startswith(")]}'")` 导致 `json.loads` 必失败——白白重试一次还误报「人机验证/解析失败」。

**根因分析**：`_strip_prefix` 与调用方拦截检测的判空逻辑不一致（一个 lstrip 一个不 lstrip）。

**解决方案**：`_strip_prefix` 改为先 `lstrip` 再判断、再切片，与检测逻辑统一。

**改动文件**：`backend/app/core/agent/tools/google_trends.py`

> **注**：该修复随后随「二、卸载 Amazon Movers 与 Google Trends 数据源」整体作废（`google_trends.py` 已删除），此处仅记录当时修复过程，勿误以为 google_trends 仍在维护。

### 五、中低：搜索词去重在翻译前（amazon_bestsellers.py）

**问题现象**：`keywords="diamond ring"` + `category="钻石戒指"` 时，part 级子串去重判不出跨语言重复，翻译后仍拼成 `diamond ring diamond ring`。

**根因分析**：去重在 `_translate_zh_keywords` 之前执行，中英文不同字符串无法互相包含判断。

**解决方案**：去重移到翻译**之后**、按**词级精确去重**（保留顺序）。注意不用词级子串去重——词级子串去重会把 `earrings` 里的 `ring` 删掉导致搜索结果失真。

**改动文件**：`backend/app/core/agent/tools/amazon_bestsellers.py`

### 六、中低：Etsy 候选池只有 2×limit（etsy_trending.py）

**问题现象**：`top = listings[:max(limit*2, limit)]`，limit=20 时池子仅 40 条，价格/收藏门槛一过滤就凑不齐 top N，与 Amazon「翻 5 页凑 100 候选再取足」原则不一致。

**根因分析**：Etsy 只拉 `_MAX_FETCH=100` 后切片 2×limit 再过滤，过滤发生在小池子内。

**解决方案**：
- 去掉 `[:limit*2]` 切片，按 `num_favorers` 排序后从**全量 100 条**扫描过滤、取前 `limit` 个幸存者；
- 图片拉取移到**过滤之后**，只为最终保留的 ≤limit 条拉主图（内部字段 `_lid` 记录 listing_id，返回前剔除），避免为淘汰品白拉图。

**改动文件**：`backend/app/core/agent/tools/etsy_trending.py`
