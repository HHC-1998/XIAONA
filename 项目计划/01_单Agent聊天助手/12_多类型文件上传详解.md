# 12_多类型文件上传详解

## 1. 目标与交互

让用户可以在聊天页把**图片、PDF、Word、Excel、文本文件**直接拖拽（或点击选择）到输入框中，随文字一起发送给模型分析。核心诉求：

- 拖拽/点击选择文件后，**输入框上方显示文件名 chips**（含大小），可点击 × 删除；
- **文字与文件可并存**（可只传文字、只传文件、两者都有）；
- 模型能识别就分析；**识别不了（如 DeepSeek 不支持图片）时，用聊天式的自然语言告诉用户**，而不是甩一段报错代码让用户懵掉；
- 上传的文件信息**进入三层记忆库**（SQL / Chroma / KG），供后续记忆检索与模型思考使用。

该能力同时作为飞书媒体监听的底座：飞书里的图片/文件也复用同一套解析与"聊天式反馈"逻辑（见 §6）。

## 2. 支持的文件类型矩阵

| 类型 | 判定（扩展名 + MIME） | 处理方式 | 模型输入 |
|------|----------------------|----------|----------|
| 图片 | png / jpg / jpeg / gif / webp / bmp / svg | base64 转 data URL | 多模态 `image_url` |
| PDF | .pdf / application/pdf | pypdf 提取文字（≤20000 字） | 全文进 LLM 上下文 |
| Word | .docx / .doc / word/* | python-docx 提取段落文字 | 全文进 LLM 上下文 |
| Excel | .xlsx / spreadsheet/* | openpyxl 提取单元格 | 全文进 LLM 上下文 |
| 文本 | txt / md / csv / json / log / yml / yaml / xml / html / py / js / ts / java / text/* | 直接 UTF-8 解码 | 全文进 LLM 上下文 |
| 音频 / 视频 / 其他 | 其余 | **不解析** | 收到聊天式"无法识别"反馈 |
| 超大文件 | 单文件 > 10MB | **拒绝** | 收到"无法识别/超限"反馈 |

> **2026-08-16 勘误**：Word 行 `.doc` 虽能识别为 word 类型，但 python-docx 只能解析 `.docx`（OOXML）——旧版二进制 `.doc` 提取会失败并返回 `[无法提取该文件内容：xxx]` 占位说明（`media_utils._extract_text` 的异常兜底），不会报错阻断。实际可靠支持的是 **`.docx`**。

> **展示 vs 模型输入分离（2026-08-15 修复）**：文本类附件（PDF/Word/Excel/文本）提取的**全文只进 LLM 上下文**（`_compose_llm_text`），**不拼进用户消息的展示/落库文本**（`_compose_user_text`）。用户对话框只显示「用户原文 + `[附件：文件名]`」占位，避免整篇 PDF 文字刷屏用户界面、污染记忆库。

**限制**：单文件 ≤ 10MB；一次最多 5 个（前端与后端双重校验）。

实现集中在 `backend/app/core/media_utils.py`：

- `detect_kind(filename, content_type)`：扩展名 + MIME 双信号推断 `image / pdf / word / excel / text / unsupported`；
- `parse_upload(filename, content_type, data)`：按种类解析，返回 `{name, kind, size, text?, data_url?}`；
- `unsupported_reply(names)`：无法识别时的聊天式友好回复文本。

> 依赖新增：`pypdf`、`python-docx`、`openpyxl`（见 `backend/requirements.txt`）。

## 3. API 契约

### 3.1 流式接口（聊天页 / 桌面助手使用）

`POST /api/chat/stream` 改为 **multipart/form-data**：

```
message      (Form, 必填)   用户文字，可为空字符串
session_id   (Form, 可选)   会话 id
source       (Form, 默认 web)
files[]      (File, 可选)   最多 5 个，每个 ≤10MB
```

SSE 帧格式（新增两类）：

| 帧 | 含义 |
|----|------|
| `data: {"session_id": "..."}` | 首帧，实际会话 id |
| `data: {"delta": "...", "thinking": "..."}` | 正常增量 |
| `data: {"media_reply": "...", "code": "media_unsupported"}` | **无法识别的文件类型**：聊天式回复，前端按正常回复气泡渲染 |
| `data: {"media_reply": "...", "code": "media_not_supported"}` | **模型不支持图片**：聊天式回复，外观与正常回复一致 |
| `data: {"error": "...", "code": "..."}` | 真错误（未配置模型 / 网络 / 服务异常），前端显示"出错 + 重试" |
| `data: [DONE]` | 结束 |

前端 `frontend/src/api/chat.js` 的 `streamChat` 已支持 `files` 参数与 `onMediaReply` 回调。

### 3.2 非流式接口（CLI / 飞书进程内直调）

`POST /api/chat` 维持 **JSON**（`{message, session_id, source}`）不变，CLI 与旧调用不受影响。飞书在进程内直调 `chat_core.chat(..., attachments=...)` 完成多模态。

> **前端发送确认（2026-08-18）**：聊天页 / 桌面助手的发送**一律走流式**——`frontend/src/api/chat.js` 的 `streamChat` 用 FormData（`message` / `session_id` / `source` 走 Form，`files[]` 走 File），前端不存在 `chatApi.send` / `chatApi.chat` 之类的非流式文件上传调用。

## 4. 能力不做厂商预判：运行时聊天式反馈

> 用户明确要求：**不要**根据厂商/模型名内置"是否支持图片"的判定表。适配就分析、不适配就明说。

实现方式（`backend/app/core/llm_provider.py`）：

- 图片直接按多模态 `{"type": "image_url"}` 发给模型；
- 模型拒绝（HTTP 400/422/415 且请求含图片）→ 抛 `VisionNotSupportedError`；
- 聊天引擎捕获后转为**正常 assistant 回复**（外观与模型回复一致，绝无报错代码）：

```
很抱歉，我当前使用的模型（deepseek-chat）不支持识别图片。您可以更换支持视觉的模型
（如 gpt-4o、qwen-vl），或上传文字类文件（PDF/Word/Excel）供我分析。
```

- 无法识别的文件类型（音频/视频等）→ 同样聊天式回复：

```
很抱歉，我目前无法识别xxx，仅支持图片、文本、PDF、Word 和 Excel 格式，请换成这些格式后再试。
```

**原则**：所有媒体类反馈都是完整、礼貌的句子，作为正常消息返回并落库；HTTP 状态码、异常堆栈只进后端日志，绝不上屏。

## 5. 附件持久化与记忆

- `Message` 表新增 `attachments` 列（Text，JSON 字符串 `[{name, kind, size}]`），迁移见 `database.py._apply_light_migrations()`；
- user 消息落库时（2026-08-15 起，`_compose_user_text`）：
  - 文本类附件**只记 `[附件：文件名]` 占位**（提取全文不再拼入 `content`，避免整篇文档进对话框/记忆库），图片记 `[附件：文件名（图片）]` 说明；
  - 附件元数据写入 `Message.attachments`，**图片二进制不落库**（只在当次请求发给模型）；
  - 提取的全文仍通过 `_compose_llm_text` 拼进当次 LLM 上下文（模型可分析）；
- **向量化 vs 实体抽取的数据来源（2026-08-28 澄清，已核对实现）**：
  - **落库 content 只记占位文本**（`_compose_user_text`），Chroma **向量化 embedding 基于占位文本**（不含提取全文）；
  - **全文只进当次 LLM 上下文**（`_compose_llm_text`/`_build_user_content`），**不进持久化与图谱**——`_persist_reply` 传给 `extract_triples` 的仍是 `_compose_user_text` 占位文本（用户原文 + `[附件：文件名]`），KG 三元组抽取**不基于附件全文**；
- Chroma / KG 三层记忆照常工作：向量化检索基于落库占位文本（附件文件名/存在性进入记忆），实体抽取同样基于占位文本（附件正文不进图谱，附件只以「文件名」这一弱信号影响记忆）。
- 接口返回：`GET /api/sessions/{id}`、`/messages`、导出均带 `attachments` 字段。

## 6. 飞书媒体按需监听（与文件上传共用底座）

### 6.1 策略（用户确认）

| 场景 | 行为 |
|------|------|
| 群聊，未 @ 机器人，发了图片/文件 | **只记元数据**：落一条「用户发送了图片：xxx / 文件：xxx」user 消息（SQL+Chroma，含 file_key），**不下载、不调 LLM、不回复** |
| 群聊，@ 机器人且要求看图/分析文件 | **按需拉取**：用记录的 `file_key` 下载 → `parse_upload` 解析 → 多模态 `chat_core.chat(attachments=...)` → 回复 |
| 单聊发图片/文件 | 直接下载解析并分析 |
| 视频（media） | **只记元数据、不拉取**（转写成本高） |
| 表情包（sticker）等 | 完全忽略 |
| 音频（audio） | 维持原有实时转写 |

### 6.2 实现

- `backend/app/api/feishu.py`：`_parse_media_meta` 解析 `image_key / file_key / file_name`；`_record_media_meta` 轻量落库（未 @ 时）；`_handle_media_message` 按需下载解析并回复；`_latest_media` + `_wants_media` 实现"@ 要求看图时自动带最近媒体"。
- `backend/app/core/feishu_client.py`：新增 `download_resource(message_id, file_key)`（原 `download_audio` 复用）。
- 元数据通过 `Message.attachments` 存 `file_key` / `message_id`，按需时据此下载，无需额外表。

## 8. 验证清单

1. 聊天页拖拽图片 → DeepSeek 收到"很抱歉，我当前使用的模型（…）不支持识别图片…"（正常回复气泡，无报错代码）；
2. 聊天页拖拽图片 → gpt-4o / qwen-vl 等视觉模型正常分析；
3. 上传 PDF / Word / Excel → 模型读出内容；上传音频 → "无法识别音频文件"；
4. 文件 chips 可删除、与文字并存发送、发送后清空；
5. 飞书群聊未 @ 发图 → 会话出现「用户发送了图片」记录；@ 机器人说"看看这张图" → 按需下载分析；视频只记元数据。
