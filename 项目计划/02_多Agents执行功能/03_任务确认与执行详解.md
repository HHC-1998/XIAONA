# 03_任务确认与执行详解

> 本详解承接 `01_多Agents执行功能项目初始计划详解.md`（总纲），记录 2026-08-17 落地的多 Agent 任务「确认 → 执行 → 审核 → 会话留痕」核心闭环的实现细节。编号遵循 02 子项目群约定（03_xx）。

## 1. 目标与范围

### 1.1 实现目标

在**不动聊天核心**的前提下接入 02 文档的三模型分工任务能力：

- **交互者（Director）**：复用 chat 模型，判断意图、提炼需求、反问确认、汇报结果；
- **执行者（Executor）**：function calling 调工具干活；
- **审核者（Reviewer）**：验收产物、不合格打回（最多 2 次重做）。

### 1.2 三种渠道的任务处置

| 渠道 | 确认方式 | 目标会话 | 留痕 |
|------|---------|---------|------|
| 聊天页（web） | 当前会话内文本确认 | 当前会话 | ✅ 全程写入当前会话 |
| 桌面助手（desktop） | 语音/文字确认 | **后端新建专属会话**（source=desktop） | ✅ 任务写入新会话，用户回聊天页侧边栏即可看到 |
| 飞书注册用户 | 飞书文本确认 | 飞书映射会话 | ✅ 写入映射会话 + 回发飞书 |
| 飞书未绑定 open_id | 不触发任务 | 无会话 | ❌ 只回 0 token 绑定引导（见 10 §5.1，2026-08-17 起取代原「飞书影子账号」行） |

### 1.3 第一期范围（2026-08-17）

- 工具只做 `fetch_url` + `generate_excel`（零新依赖，符合 AGENTS.md 依赖例外流程）；
- 确认交互为**文本/语音问答**（「是/好/执行」即确认，全渠道统一）；确认卡片为后续增强；
- 执行异步后台（`asyncio.create_task`），聊天页靠轮询刷新；
- 产物落盘 `backend/artifacts/{user_id}/{task_id}/`。

> **2026-08-19 追加**：新增电商数据源工具 `fetch_amazon_bestsellers` + `fetch_etsy_trending`（均零新依赖，httpx + stdlib），见 §5.4/§5.5 与 `02_北美电商数据网站爬取详解.md`。

## 2. 任务状态机

```
pending(待确认) → confirmed(已确认) → executing → reviewing → revising(N, ≤2)
                 → done / failed
    （用户回复取消）→ cancelled
```

- `pending`：交互者提炼需求后创建，等待用户确认；
- `confirmed`：用户确认执行，后台任务启动前；
- `revising`：审核打回、执行者带审核意见重做（`retry_count` 递增）；
- `done` / `failed`：审核通过 / 执行或多次打回后失败；
- `cancelled`：用户明确取消（只有 pending/confirmed 可取消，见 `api/agent.py`）。

## 3. 渠道分流与留痕

### 3.1 消息处理顺序（`service.handle`）

每条用户消息只走一条路径：

1. **有 pending 确认任务** → `director.classify_confirmation` 判定（**仅限当前会话 + 渠道**，`_latest_pending(user_id, session_id, channel)` 过滤，避免用户在别的会话/飞书/桌面误确认或误取消，2026-08-19 起）：
   - `yes`：确认执行 → `_confirm`（确定目标会话 + 后台启动）；
   - `no`：置 `cancelled`，回复取消；
   - `other`：保持 pending，再次反问提示。
   - 确认判定关键词顺序（2026-08-19 起，2026-08-28 补否定组合预检）：**否定组合预检（先拦「不+确认词」：不行/不可以/不好/不确认/不执行/不同意/不开始，去空白匹配兼容「不 行」）→ 强肯定短语（没问题/可以/好的/好/行/确认/执行/开始/ok/yes）→ 强否定短语（不是/不用/不要/取消/算了/放弃/不了/等等/再说/no）→ 弱否定（不/没/否）→ 弱肯定（是）**。「没问题」是最常用肯定答复且含「没」，必须由强肯定短语先拦截，否则被误判为取消；「不行/不可以/不好」等含单字确认词，也必须先被否定组合预检拦截，否则会被强肯定短语误判为确认（见当天台账一）。
2. **无 pending 但意图命中** → `director.refine_task` 提炼 → 创建 pending → 反问确认；
3. **都不是** → 回落 `memory_engine.chat/chat_stream` 正常聊天链路。

### 3.2 目标会话确定（`_confirm`）

- **desktop**：`sql.ensure_session(user_id, "", "desktop")` **新建专属会话**，任务全程写入；
- **web / feishu**：沿用当前/映射会话；
- **飞书未绑定 open_id**：不触发任务（0 token 绑定引导，见 10 §5.1；2026-08-17 起取代原「shadow 飞书影子账号」逻辑）。

### 3.3 会话留痕内容

后台任务每阶段向目标会话写 assistant 消息（`workflow._write_message`，**async + `asyncio.to_thread`**——落库与 Chroma embedding 走线程池，避免 embedding 调用阻塞事件循环导致全站卡顿，2026-08-19 起；向量由配置的 embedding 模型经 `/v1/embeddings` 生成，`_write_message` 传 `embedding_cfg=cfgs.get("embedding")`，未配置则跳过，2026-08-23 起）：

```
▶ 开始执行任务：<描述>
🧐 执行完成，正在验收…
↻ 审核未通过（第 N 次重做）：<问题清单>（如有打回）
✅/❌ <最终总结>
📄 已生成产物：
- [产物名](/api/agent/tasks/{id}/artifacts/{name})
```

`service` 侧确认回复（「好的，开始执行任务…」）连同用户确认消息一并写入目标会话。

### 3.4 桌面助手专属会话

- 用户说任务（第一轮）：确认文案写入桌面固定会话；
- 用户语音确认（第二轮）：**新建专属会话**，确认对话 + 任务过程 + 结果全部写入；
- 桌面助手 SSE 首帧/`task_started` 帧回传新会话 id → `onSession`/`onTaskStarted` 更新前端，用户回聊天页侧边栏即可看到该任务会话。

### 3.5 飞书未绑定 open_id（2026-08-18 起，已实现）

未绑定 open_id 发消息 → **0 token 绑定引导 / 绑定状态机**（`api/feishu.py` 的 `process_feishu_event` + `_handle_bind_turn`）：**不创建账号、不调 LLM、不触发任务**。

- 无在途绑定状态：回固定引导文案（「你还没有连接到小娜账号…回复「绑定」或直接回复注册手机号」，见 `10_飞书IM机器人接入详解.md §5.1`）；
- 绑定状态机三步：报手机号（查账号存在）→ 报密码（`verify_password` 校验）→ 短信验证码（`verify_sms_code` 校验）→ 写入 `feishu_user_map` 绑定成功；
- 绑定中间态按 open_id 存内存（5 分钟 TTL，重启清零），密码/验证码不落库、不进记忆、不进日志；
- 群聊未 @ 机器人的未绑定消息直接忽略不回复。

## 5. 工具层

### 5.1 注册表（`tools/registry.py`）

```python
_SPECS, _HANDLERS = _make_tools()   # _SPECS: [{name, description, parameters}]；_HANDLERS: name → 函数
TOOLS = [{"type": "function", "function": spec} for spec in _SPECS]  # OpenAI 标准 tools 格式

def list_tools() -> list[dict]: ...               # 注入执行者模型的 tools 参数
async def call_tool(name, params, ctx) -> dict: ...  # 白名单分发，错误结构化返回不抛异常
```

- **tools 必须用 OpenAI 标准 `{"type":"function","function":{...}}` 包装（2026-08-19 起）**：DeepSeek 官方端点严格反序列化校验，直接传 `{name,description,parameters}` 会 400 `tools[0]: missing field `type``（曾导致执行者整轮失败、任务回「❌ None」，见当天台账）；Ollama / OpenAI 兼容端点均接受标准格式。`call_tool` 分发仍按 `spec["name"]` 匹配，不受包装影响。
- ctx：`{user_id, session_id, task_id, artifacts_dir}`，供需要落盘/读会话的工具使用（`session_id` 由 workflow 注入，`fetch_session_messages` 依赖；缺 ctx 时工具只校验数据不落盘）；
- 未知工具/异常统一返回 `{ok: false, error: "..."}`——工具结果要回填给模型继续决策，不能抛异常中断循环。

### 5.2 fetch_url（`tools/fetch_url.py`）

- httpx 抓取（30s 超时、UA 伪装），正则剥离 HTML（去 script/style/标签、折叠空白）；
- **SSRF 防护（2026-08-24 起）**：抓取前解析 URL host 并 DNS 解析，拒绝回环/内网/链路本地/保留/云元数据（169.254.169.254）地址；
- **重定向手动跟随（2026-08-24 起）**：`follow_redirects=False`，手动循环处理 3xx（最多 5 跳），每跳重新做 SSRF 校验——防公网 URL 302 到内网地址绕过防护，超跳数返回结构化错误；
- 默认截断 8000 字符（防上下文爆炸），返回 `{ok, url, title, text}`。

### 5.3 generate_excel（`tools/generate_excel.py`）

- openpyxl 生成 xlsx，`headers + rows`（rows 支持二维数组或对象数组）；
- 产物落盘 `artifacts/{user_id}/{task_id}/{filename}`，返回 `{ok, path(相对), size, sheet, rows}`；
- 文件名白名单清洗（`_safe_filename` 防路径穿越）；行列数不一致、rows 为空均返回结构化错误。

### 5.4 fetch_amazon_bestsellers（`tools/amazon_bestsellers.py`，2026-08-19，2026-08-23 增强）

- Amazon 电商数据源（内置保底、无需 key）。主路径**搜索页按人气排序**（`/s?k={关键词}&s=exact-aware-popularity-rank`），显式 `url` 传 BSR 类目页时走榜单页解析；
- **地区站点（2026-08-23 起）**：`site` 参数支持 us(默认)/uk/ca/au/de/fr/it/es（兼容 `amazon.co.uk`/`britain`/`germany` 等别名归一），请求带对应站点货币 `i18n-prefs` + 语言 `lc-main` cookie 与 `Accept-Language`（服务器出口 IP 非对应地区时默认返回本地货币，实测香港 IP 返回 HKD），商品链接清洗域名随站点；
- **过滤（2026-08-23 起，2026-08-24 补区间/颜色/材质/排除词/过滤顺序）**：`min_price/max_price`（数值，单位随站点货币，如 uk 英镑）/`min_rating`/`max_rating`（评分区间 0~5）/`min_reviews`/`max_reviews`（评论数区间，支持 1000 或 "1000"）/`color`/`material`（颜色/材质，中文/英文均可，并入搜索词缩小范围）/`exclude_keywords`（排除词，逗号/空格/顿号分隔，中英文均可，如 玩具/toy,派对,耳环，标题含任一排除词直接丢弃，**不并入搜索词**、仅本地过滤，`_ZH_TO_EN` 含排除类词兜底翻译）；无法解析的字段不参与过滤避免误杀，过滤条件拼进返回 `note`；**过滤顺序（2026-08-24 起）：先排除词 → 再价格/评分/评论区间 → 最后才截断取 top N + rank 从 1 重排**（此前先 `[:limit]` 截断再过滤，top10 混入玩具/耳环一过滤就凑不齐 N 个）；
- **搜索路径翻页（2026-08-27 起，见当天台账三十）**：搜索路径翻 `_MAX_SEARCH_PAGES=5` 页（约 80~100 候选，单页仅 16~20 个——排除词一筛候选池就空了、top10 只给 1 条），逐页解析后按 `product_url`（ASIN）去重合并，页间 `_PAGE_DELAY=1.2s` 节流防反爬；单页失败/被拦用已抓到的页继续，候选池为空才报错；BSR 类目页路径保持单页；
- **标题兜底（2026-08-24 起）**：`_SearchParser` 除 `h2` 内捕获标题外，`a` 标签命中 `/dp/` 且未在捕获状态时以链接文本为标题兜底、`h2` 的 `aria-label` 非空时直接取用（新版页面标题不在 `h2` 内不再导致商品名缺失）；
- **中文品类词由执行者翻译成英文关键词**（任意品类全覆盖：玩具→toys、文具→stationery、银戒指→silver ring 等，见 §5.6）；工具层 `_ZH_TO_EN` 饰品映射表保留作兜底（执行者漏翻时救饰品类词）；
- 内置 `bm-verify`/Robot Check 反爬挑战检测返回中文提示；
- 返回 `{ok, source:"amazon", query, items:[{rank, title, price, image_url, product_url(/dp/ASIN), rating, reviews}], markdown_table?, note?}`（`markdown_table`：严格 7 列 Markdown 表格，2026-08-24 起由后端生成，workflow 自动附加）。详见 `02_北美电商数据网站爬取详解.md §7.1`。

### 5.5 fetch_etsy_trending（`tools/etsy_trending.py`，2026-08-19，2026-08-23 增强）

- Etsy 官方 Open API v3（需 key）。**key 解析回退链**：`ctx.user_id` 查 `data_source_configs` 表（设置页「数据源 API」per-user 配置）→ `.env` 的 `ETSY_API_KEY`；均未配置返回结构化降级错误（执行者改走 Amazon 源）；
- 按 `num_favorers`（收藏数）降序近似「最受欢迎」；批量取主图 `/listings/{id}/images`（并发 5、限频 0.2s）；
- **过滤（2026-08-23 起）**：`min_price/max_price`（Etsy `price.amount` 是「分」，按 `amount/100` 数值比较，不做汇率换算，note 说明按 listing 本币比较）+ `min_favorers`（最低收藏数）。Etsy 是全球平台**无地区概念**、官方 API **无评分字段**（只能按价格/收藏过滤，用户要评分时用 Amazon 源；颜色/材质并入 `keywords` 英文，2026-08-24 起）；
- 返回 `{ok, source:"etsy", query, items:[{rank, title, price, image_url, product_url, num_favorers, views, taxonomy}], markdown_table?, note?}`（`markdown_table`：严格 8 列 Markdown 表格，2026-08-24 起由后端生成，过滤后 rank 统一重排 1..N）。详见 `02_北美电商数据网站爬取详解.md §7.1`。

### 5.6 交叉验证工作流（`executor.py` 系统提示，2026-08-19）

- **Amazon 主榜必调 + 可选叠加（2026-08-27 起，2026-08-28 随 Movers/Trends 卸载收窄）**：任何榜单/选品任务第一步**只调 `fetch_amazon_bestsellers`**（现状主榜，免 key）；`fetch_etsy_trending`（需 key）/ `fetch_pinterest_trends`（需 token）为**可选叠加层**——未配置对应 key/token 时工具返回降级错误、直接跳过勿重试；用户没明确要多源交叉验证时不必强行叠加。
- 多源场景输出**按源分榜**（Amazon 榜 / Etsy 榜各自榜单表格，2026-08-24 起由后端生成 `markdown_table`，执行者禁止手拼，见下）；对多榜共同高频品类特征标「双源确认」，单源标「单源信号」；末尾给「多平台共同趋势」总结；未配置的源自然只用 Amazon 并如实说明。
- **中文品类词翻译（2026-08-19 追加）**：执行者调用数据源工具时把用户的中文品类词**翻译成英文关键词**（任意品类全覆盖：玩具→toys、文具→stationery、银戒指→silver ring、积木→building blocks），不要直接传中文，也不用泛词（用户说「银戒指」用 silver ring，不用 jewelry/ring）；工具层 `_ZH_TO_EN` 映射表保留作兜底。
- **地区与筛选（2026-08-23 追加，2026-08-24 补区间/颜色/材质/排除词）**：用户指定地区（英国/加拿大/澳洲/德国/法国/意大利/西班牙）→ `fetch_amazon_bestsellers` 传 `site` 参数（uk/ca/au/de/fr/it/es），未指定默认 us；用户指定价格/评分/评论数**区间**（如「15~20 美元」「4.5~4.6 分」「评论不低于 3 万」）→ `min_price`/`max_price`/`min_rating`/`max_rating`/`min_reviews`/`max_reviews` 参数，指定颜色/材质（白色/玫瑰金/925银等）→ `color`/`material` 参数（中文/英文均可）；用户说「只要 X、不要 Y」（如「只要正经首饰戒指，不要玩具/派对装饰/项链/耳环」）→ 不要的词传 `exclude_keywords`（如 玩具/toy,派对,耳环），工具**先排除再取足条数**，**不要从工具返回结果里手动砍**（手动砍会导致 top10 只剩 5 个）；**未指定的维度一律不传（即不限制）**，**不要自己从结果里挑**；Etsy 无地区、无评分字段（只能按价格/收藏过滤，要评分用 Amazon 源，颜色/材质并入 keywords 英文）。
- **榜单表格由后端生成（2026-08-24 改，替代 LLM 手拼）**：`fetch_amazon_bestsellers`/`fetch_etsy_trending` 返回 `markdown_table` 字段——严格列对齐、链接列直接显示**完整 https:// 商品网址**（`[完整URL](完整URL)` 可点可复制）、缺失字段填「-」；Amazon 7 列：排名|图片|商品名|链接|价格|评分|评论数，Etsy 8 列：评分列「-」另加「收藏/来源」。executor 的 `run()` 收集 `tool_results` 带出，workflow 最终消息**自动附加全部来源榜单表格**（`_format_ranking_table`，2026-08-27 起：正序遍历收集所有 ok 且带 markdown_table 的榜单结果、每张前标来源中文标签、**同源保留最后一次**——执行者最后一次调用通常排除词更全、筛选更严，曾出现第一次宽松结果混入耳环/玩具与严格总结错位；final_msg 已含表格分隔行则跳过）。执行者**禁止手拼表格**（不写 | 行、不复制 URL，LLM 少写一个 | 就整行右移、长 URL 被省略），最终总结只写文字结论（条数/主要发现/双源趋势）；**各来源各一张表**（多表对照展示，不再只附最后一份）。

### 5.7 文档整理类工具（`generate_pdf` / `generate_docx` / `fetch_session_messages`，2026-09-01 补 content）

- **数据源优先会话已有内容（2026-08-24 起）**：用户说「把上面的/刚才的/这个榜单整理成文档」= 当前会话已有内容，执行者必须先调 `fetch_session_messages` 读会话作数据源，**禁止再调数据源工具重新抓取**（director 提炼 params 会带「内容来源: 会话已有内容」）。
- **表格自动注入（2026-08-24 起）**：`fetch_session_messages` 提取会话 markdown 表格（**同时扫描 user 与 assistant 消息**，2026-09-01 起——用户粘贴在聊天框的原文表格同样进 `markdown_tables`）为 `markdown_tables`，executor 调 `generate_pdf`/`generate_docx` 前**自动注入 `args["markdown_tables"]`**（LLM 无需感知）；**executor 已传 `content` 原文时不再注入**（content 里的表格由代码直接渲染，避免重复）。
- **content 原文渲染（2026-09-01 起）**：用户提供的是大段粘贴文本（报价/方案/报告等，通常 >2000 字或含大量表格）时，执行者把读到的用户消息原文按序拼接放进 `content` 参数，由后端 `_parse_markdown_blocks` 直接解析渲染（`#` 标题 / markdown 表格 / `- ` 列表 / 段落），**禁止手工把超长全文转成 sections JSON**（输出 token 超限截断 JSON → 「sections 不能为空」反复失败）；短文本（无表格、数百字内）仍用 sections 结构。sections 元素非 dict 时后端跳过不抛异常（修 `AttributeError: 'str' object has no attribute 'get'`）。详见 `04_生成PDF文件详解.md` 与 `05_生成Word文档文件详解.md`。
- **会话原文 content 兜底注入（2026-09-01 二轮修复）**：executor 收集会话 user 消息 >300 字正文拼接，generate_pdf/generate_docx 的 `args.content` 为空或明显短于原文（疑似截断）时**自动注入原文**——不再依赖 LLM 把超长全文手工回传（输出 token 超限必截断 → args={} → 文档工具「sections 不能为空」）；content 注入时只附加 `assistant_tables`（用户表格已在原文里，避免重复渲染），否则附加全部 `markdown_tables`。
- **输出格式硬锁（2026-09-01 起）**：用户要 word/文档/文件（未明确格式默认 Word）→ **只用 `generate_docx`**；要 pdf → **只用 `generate_pdf`**。**禁止因某格式工具失败而改调另一种格式工具**（交付格式与用户要求不符是严重错误）——失败时改参数重试（content 传原文 / sections 精简），仍失败如实报告失败原因与建议。
- **换行保真依赖前端 textarea（2026-09-01 起）**：用户粘贴的多行文本能否被识别为表格/标题，前提是**聊天输入框为 textarea 换行保真**（`ChatInput.jsx` / `DesktopAssistant.jsx` 均为 Enter 发送、Shift+Enter 换行的多行输入框，见 05_前端详解）——旧单行 `<input>` 会把 `\n` 剥光，DB 里用户消息零换行，后端 `_parse_markdown_blocks` 无法识别任何结构；文档工具对**纯文本表格**（无 `|` 管道符，Tab/全角空格/单空格对齐）与**中文编号标题**（`一、`/`第X章`/`（一）`→H1，`1.1` 短行→H2）做结构识别渲染，不自信则回落段落。
- **默认原文直通 · 方案 C（2026-09-01 起，六轮升级为「正文永不经过 LLM」）**：用户「粘贴大段原文 → 生成 Word/PDF」默认**原样直通**——executor 的 `_want_passthrough(task)` 判定（task_type 为 generate 且描述/params 不含总结/提炼/精简/概括/改写/润色等加工词）为真时，调文档工具**无条件注入会话用户消息原文到 `content`**（并移除 sections/markdown_tables/title/subtitle/date/source），正文完全用会话原文渲染，LLM 只定格式与 filename，**不重写/不总结正文**（根治「生成文档内容被 LLM 改写、20+ 表格只剩 1 个」）；只有用户明确要求「总结/提炼/精简」等加工词才走 LLM 提炼。
- **规则打底 + LLM 标记指令兜底（2026-09-01 六轮方案 C）**：直通注入前 `_markup_document` 先本地规则解析（`_smart_break_lines` 零换行语义分行 + `_parse_markdown_blocks` 结构化：纯文本表格/中文编号标题/连续 `|` 表格），**只有规则吃不准的表格**（候选行 ≥4 且规则识别覆盖 <80%）才调一次 LLM——LLM 只返回行级标记指令 `{line, anchor}`（`_ask_table_marks`），程序在原行插 `|` 表格标记后重解析校验，**LLM 输出正文一律丢弃**；失败/超时/非法 JSON 回落原文直注（宁可保真不保结构）。`_markdownify_content`（LLM 转 markdown）仅剩**加工模式**使用，且改为并行分块（`Semaphore(4)` + `wait_for(180)`）提速。

## 6. 执行者 / 审核者

### 6.1 执行者（`executor.run`）

function calling 循环：

1. 注入系统提示（任务执行者角色）+ 用户任务（task_type / description / params）；
2. `llm.chat_with_tools(messages, cfg, tools=TOOLS)` → 返回完整 message；
3. 有 `tool_calls` → 逐个 `call_tool` → 结果以 `role: "tool"` 回填 → 继续；
4. 无 `tool_calls` → 取 `content` 作为最终总结返回。

每轮动作经 `on_log(role, action, payload)` 回调记录到 `AgentRunLog`。上限 6 轮工具调用（防无限循环）。

**进度回调（2026-08-23 起）**：`on_log` 为**可 await** 回调（`executor.run` 内 `await on_log(...)`），动作包括：
- `think`：`{round}` 第 N 轮决策；
- `call_tool`：`{tool, args}` 调用工具前；
- `tool_result`：`{tool, ok, error}` 工具返回后（新增，供 workflow 在失败时写"正在尝试其它方案"进度消息）。

**条数不足如实交付（2026-08-23 起，2026-08-24 补先过滤后取足条数）**：系统提示要求工具返回 `ok:true` 且 `items` 非空时**直接交付**（工具已按用户价格/评分门槛过滤，返回即符合条件的真实结果），条数少如实说明「符合全部条件的商品仅 N 条」，**不要反复换关键词重试**（曾导致严苛条件任务 6 轮换词耗尽报「达到最大工具调用轮次」，见当天台账七）；仅 `ok:false` 或 `items` 为空才换关键词/换数据源（最多 1-2 次）。**取足条数（2026-08-24 起）**：工具**先排除再取足条数**——用户要 top10 就应给足 10 条（搜索页能解析出几十张卡，排除玩具/耳环后从符合的池子里取 top N），只有过滤后池子本身不足 N 条才如实说明；执行者**不要从工具返回结果里手动砍**，排除交给 `exclude_keywords` 参数。

### 6.2 审核者（`reviewer.review`）

- 输入：任务目标 + 执行者总结 + 执行日志（截断 3000 字）；
- 输出：`{passed, issues[], comment}`；审核异常时保守通过（防任务死循环）。

### 6.3 打回重做（`workflow.start_task_async`）

- 最多 `AGENT_MAX_RETRY`（默认 2）次重做，打回次数超限即终止；
- **审核意见回传**：打回时把 `result["issues"]` 并入下一轮 `refined["review_issues"]`，executor 下一轮在 **user message content** 中读取 `task["review_issues"]` 作为约束（`executor.run` 拼「审核意见（上一轮验收未通过，必须逐条修订后再交付）：<issues>」到用户消息，**不是**注入 system prompt，2026-08-19 核对）；
- 重做时把审核意见一并写入目标会话消息（`↻ 审核未通过（第 N 次重做）：<问题清单>`）。
- **执行者异常处理（2026-08-19 起）**：`executor.run` 抛异常时 except 分支把 `result` 置为 `{success:false, summary:"执行出错：<真实错误>"}` 后**不再 break**，落入下方统一失败处理设置 `final_msg`——此前 break 会跳过 `final_msg` 赋值导致会话留痕写成「❌ None」（见当天台账）。
- **进度消息流（2026-08-23 起）**：`workflow._on_log` 改为 `async def`，除落 `AgentRunLog` 外，拦截 `call_tool` 写 `🔧 正在{中文标签}{参数摘要}…`、`tool_result` 且 `ok=false` 写 `⚠️ {中文标签}未成功（原因），正在尝试其它方案…`（成功不额外写）。工具名经 `_TOOL_LABELS` 中文映射（`_tool_args_summary` 提炼 `keywords/url/category/filename` + 过滤参数 `site/min_price/max_price/min_rating/max_rating/min_reviews/max_reviews/min_favorers/color/material/exclude_keywords` 等摘要，2026-08-24 补 max/颜色/材质/排除），不暴露英文函数名。
- **进度 touch 任务 updated_at（2026-08-23 起）**：`_write_message` 新增 `task_id` 参数，写消息后 `_touch_task` 独立 DB 会话 touch `AgentTask.updated_at`；所有写进度/结果消息的调用点均传 `task_id`——前端 2s 轮询仅在 `updated_at` 变化时刷新会话消息，进度气泡逐条出现（修复"任务执行期间前端一次不刷新、结束时一次性输出"）。
